# 独立测试：范围、原始证据与评价

## 是什么、做什么、怎么做

独立测试由评价方依据测试前已确认并固定的要求自行设计，判断指定交付是否符合要求。工作包是交付内容、责任边界和验收标准明确的一项任务，沿目标项目已有任务载体，不强制另建文件夹体系。PRD 完整产物的独立评价按第 5 节使用；开发、联调测试、迭代在明确安排独立评价时使用。产物作者或开发者的自检不因换名称、另开命令或换模型就成为独立测试。

用户决定被测任务、固定要求／禁止情形、评价方及允许动作，裁决范围和验收；产物作者或开发者交对象身份、评价／运行条件及自己的检查证据并负责获准整改；评价方独立设计、保全、执行和如实报告。评价方本轮不参与被测产物／实现及作者自检／开发者测试的编写，不能代改交付或自行放宽规则。本规则形成不授权实际测试、委派、真实集成、外部调用或发布。

顺序为核固定输入／许可 → 独立设计并证明覆盖 → 说明操作、范围及存在的准确命令 → 正式执行前保存原始文件 → 实际执行及分项判断 → 报告评价有效性 → 获准整改／受影响重测 → 交用户作独立的验收或后续决定。人工 PRD 评价的操作与保全时点沿第 5 节。共用根因、检查及返修动作沿 [execution](execution.md)，只读／写入边界沿 [core](core.md#只读模式与步骤权限)。

## 1. 固定要求与独立设计

核工作包、被测对象／版本、有效任务说明、验收及关键禁止情形的具体位置、确认依据和允许环境／读写／运行范围。被引用文档仅其明确纳入本任务的行为属于范围，不能把整份上游或全项目自动纳入。要求不明先报告对应缺口并取得决定，不用开发者的预期解释替用户固定要求。

制定测试方案须结合当前项目的实际需求、风险、技术条件和时间／成本约束，参考与测试对象相关的 [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)、[Google](https://testing.googleblog.com/2024/10/smurf-beyond-test-pyramid.html) 等官方成熟最佳实践建议，注明参考来源与适用理由，按项目实际选择方法、范围和用例；不照搬固定用例数、测试比例或工具流程，不以外部建议替代已确认需求与验收标准。

评价方逐项依据上述要求自行设计用例，不复制、改写或包装作者自检／开发者测试，不直接采用作者／开发者预期结果。每项写清对应要求、前置／操作、由该要求推导的预期、观察方式及原始证据位置；无法指向具体有效要求的用例不属于本轮，不执行。可以读取交付的接口与评价／运行条件说明，但作者自检及开发者测试／构建／格式／类型检查只作补充，不能计入独立用例、补足覆盖、关闭独立问题或抵消失败。

首次评价列出本工作包全部可测试行为、验收及关键禁止情形与用例的对应关系；不得以少量抽查或用例数量冒充完整覆盖。不机械为每项凑成功／拒绝／异常对，按要求决定。无法测试、缺环境或缺许可的行为列出限制，不能以删除这些项宣称整包验证通过。

## 2. 范围、命令与执行前保全

正式执行前向用户说明本轮测什么、不测什么、被测版本／环境、准确命令（含参数及执行位置）、计划／全部评价方测试文件、证据目录与必要权限；现有明确许可覆盖的动作无需重复审批。写入、测试和证据保全的许可不足时先准备可审方案，暂停依赖动作。人工文档评价的操作说明及保全时点按第 5 节适配，不虚构可执行命令。

在首个正式命令之前，把该轮计划和全部评价方测试文件的原始内容副本保存到工作包已有证据位置，与实际执行文件分开；核副本实际存在、内容一致且可恢复，再执行固定命令。不仅保存校验值，不在执行后补做副本，也不为了保全而修改／提交产品仓库或外发资料；目标项目可在获准隔离位置保存证据并由已有记录索引。

执行中不自行追加命令或扩大范围；需要改变正式命令／计划时先停止受影响执行，说明变化。扩范围须取得用户明确授权，规则或报告不能自授权全量测试、额外集成层、跨工作包检查或阶段／发布门禁。保存输出等既定证据动作在计划中说明，不用它们包装额外测试。

已正式执行的计划／测试文件不改写、重排或重新生成。确需调整，保留上一轮完整文件并建立明确的新版本／绑定；测试自身错误同样不能直接覆盖旧文件后宣称原轮通过。发生执行后改写时保留原始副本并披露偏差；若宣告旧绑定作废仍保留该轮记录，不销毁失败历史。无法从仓库或其已登记的获准证据归档恢复执行前原文件的通过轮次，不能作为正式证据。

## 3. 执行事实、结果与评价有效性

先实际执行、读取原始结果并核检查生效／覆盖，再逐项给结论；命令发起、计划存在和开发者通过标签不能证明独立验证。以下为评价层结论，不改程序自身执行／判定两轴、错误码或退出码。

| 评价结论 | 条件及报告方式 |
| --- | --- |
| verification_fail（验证失败） | 有可定位证据表明被测行为违反固定要求；指出要求、实际／预期、影响及证据，不用其他通过项抵消 |
| evidence_incomplete（证据不完整） | 用例错误、测试执行出错、必要行为未测或证据不足；定位评价问题与未覆盖范围，不误说产品已违反要求 |
| verification_pass（验证通过） | 对声明范围的全部必要行为均取得合格证据、无违反要求、评价有效且原始文件可恢复；只通过几个用例不能扩成未测要求通过 |

产品失败和证据不完整可以同时存在，均保留。依赖开发者结果代判、遗漏本轮行为、执行未授权范围或隐瞒测试错误会使相应评价决定无效；单独报告有效性问题、范围及影响，不能改称通过。不要因测试工具出错删除已观察到的产品失败，也不以开发者重跑成功关闭独立缺陷。

评价方以无已确认来源或超出本次范围的内容作标准而判失败时，该项评价无效，按 evidence_incomplete 报告并撤销该误判，保留原记录；依有效要求取得的其他失败证据仍成立。不能把评价依据错误归为产品失败，也不能据撤销误判宣称产品通过；更正评价按第 2 节保留原文件和新版本，再核受影响项。

报告沿工作包已有证据载体保存，注明固定要求／被测版本、评价方身份及独立性说明、首次或重测、实际操作及存在的命令、原始计划／测试副本、逐项结果、未覆盖／未执行、有效性及限制。只读模式无法获准保全文件时交准备材料，不能跳过前置直接生成正式通过证据。

## 4. 整改重测与权限止点

重测只包含尚未解决的问题、整改改变的行为及可能因该改动改变实际结果的必要回归。逐项写因果依据；同文件、同模块、同工作包或改了文档名称不构成重测理由。不自行扩大为整包重测，影响无法界定先补必要分析，扩范围交用户裁决。复用未受影响证据须仍覆盖现行对象／条件，并说明依据。

多轮局部整改要核累计变化是否使首次覆盖或未受影响证据失效；不能只看最后一次差异。影响无法界定或覆盖出现缺口时，报告失效部分、所需补证／范围和代价，交用户决定；不预设周期、不自动整包重跑，也不以旧首次通过维持当前整包通过。

重测仍由评价方依据固定要求独立设计，重新落实范围／命令及执行前原始副本，沿新版本保留旧失败和处理关系。报告明确“整改范围重测”及本轮能支持的结论；原首次评价不完整时，局部重测通过不能填补其他未测行为或宣称整包独立通过。

独立测试通过只表示指定验证通过，工作包验收、阶段结果、发布决定和后续动作许可各须真实决定，不自动开始下一任务、推送或部署。

### 其他阶段独立测试提议

PRD 完整产物及开发—迭代之外需要独立测试时，先报对象、为何普通核对不足、范围／操作／证据／代价与推荐，交用户裁决后再安排；不先执行再报告。

## 5. PRD 阶段完整产物的独立评价

### 对象、输入与分工

本项检查 PRD 阶段完整产物是否准确、完整地把已确认要求转成可理解、可验收的规格。在完整稿形成、作者自检之后，提交用户作指定版本阶段确认之前安排；需求澄清／暂存时不逐批启动。已通过的历史 PRD 不因本规则新增自动重开。独立评价的通过不替代用户确认，也不证明未来产品已实现或真实行为已验证。

评价方先依据有效 MRD／等效上游、本阶段确认需求及变更／取舍、目标项目已明确采用的 PRD 成果约定，固定判断依据，再开展正式稿件核对。成果约定须给具体位置／采用依据；使用本技能 PRD 方法时，对应[第 2—4 节](../skills/prd.md#2-从用户任务展开具体行为)的行为、验收／追踪及成文要求，不以被测稿或作者自检清单补造标准。

固定的是已有需求依据，不要求先批准被测 PRD 才能评价。稿中自行新增的要求／验收不能反向成为正确性依据。上游未决定的关键问题交用户裁决，评价方不替用户补业务或放宽要求。

先前已读过该稿须披露接触范围，阅读本身不使评价失效；仍须符合第 1 节独立设计和未参与编写的责任边界。

作者提交指定版本的完整产物清单：PRD 正文、实际拆出的业务／异常／非功能／验收／适用模型契约正文、需求追踪及本阶段配套的必要决定／变更／确认状态、计划验证与交接说明。沿现有载体列路径／版本／章节及对应来源，不要求拆成多个文件。评价方依据确认清单和阶段要求核产物清单是否完整，不能接受作者漏列某份正文来缩小范围；缺失必需产物本身是评价对象，不能从清单删掉后称全部通过。

首次评价覆盖这份完整产物的全部本版需求、必要分支、验收及跨条目关系，不仅是当前首功能、新改的几行或抽样。MRD 和确认记录供核来源及一致性，不对其整份质量重新测试；架构／模块／组件／UI、代码、模型执行、宿主接入、市场效果不属于本项。尚未进入本版的事项核其有效取舍与状态，不要求实现。产品计划中的后续测试只评价其是否可据需求执行，不在本阶段运行那些测试。

用户决定未定业务、范围变化、评价方及许可、阶段是否通过；作者交完整产物和来源并负责获准整改；评价方独立核覆盖、执行和报告，依第 1—4 节保持职责与证据独立。评价方不能一边改稿一边签独立通过；作者自检只作补充。

### 覆盖、方法与原始材料

评价方在项目已有评价／证据载体独立列“固定要求及依据 → 对应产物位置或缺失 → 核对操作／用例 → 由要求推导的预期 → 观察／证据位置”。计划中未核的位置可标待定位，正式评价的实际落点及结论记执行报告，不回改原计划。覆盖按实际适用内容组织：

| 核对对象 | 本阶段的具体操作 |
| --- | --- |
| 需求来源与完整性 | 从已确认任务／需求逐项找到行为及验收落点，反向核稿中内容的来源／范围；核有效变更、移出理由和确认状态，不能只查编号数量 |
| 用户任务、行为与可理解性 | 按稿中角色、前置、输入、操作和响应走到结果，核核心任务真正展开、人与产品责任清楚，前置需求本版有效；指出会导致不同操作／结果解释的歧义及影响，不能靠评价方自行猜测补齐 |
| 相关异常及状态／数据／权限 | 对已确认或有效方法要求适用的失败、取消、超时等分支，核触发、可见结果、影响和后续动作；不为不适用业务硬加分支 |
| 验收与适用非功能／模型契约 | 从固定要求自行推导场景，核稿中预期是否忠实、可观察、有验证条件；数值／边界有确认依据，不能采用作者的自定成功线 |
| 追踪、跨条目一致与交接 | 核来源—需求—验收—计划验证的双向关系，术语、权限、状态、前后条件无冲突；稿中被当成本版有效要求／验收的新增内容须有确认来源且符合范围，拟议／待决／假设／未验证与确认分开，交接能定位有效规格 |

这些是适用核对对象，不是要求所有产品具备全部业务类别的新模板。每项具体用例仍须指向第 1 节的固定要求；正文通读、表格普查与链接检查可辅助定位，不能代替逐项语义判断和完整覆盖。人工沿规格推演应标“文档语义核对／纸面走查”，不冒称产品运行。

正式评价前说明产物清单、固定依据、覆盖与排除、逐项人工阅读／对照／推演操作及辅助命令。纯人工部分明确“无程序测试命令”，列实际工具、文件／章节、操作顺序和记录方式；用脚本时另列准确命令／参数／目录。先准备方案所做的读取不计正式通过证据。

在首项正式评价操作之前完成第 2 节保全：保存评价计划、覆盖关系、全部用例／预期／人工操作说明及存在的脚本原件，与执行记录分开；同时绑定可恢复的指定产物版本和固定依据，沿已有不可变版本或获准内容副本，不只记版本名／哈希。人工评价不能等读完判定后才补存方案；执行后的改动沿第 2 节保留旧文件及新版本。正式评价不改被测稿；稿件或依据变化时停止受影响项，核旧证据有效性再按第 4 节接续。

### 判定、整改与交接

实际读取／对照／走查后，逐项记录固定要求、正文位置、预期与观察、原始依据及第 3 节结论。已确认需求被遗漏、核心行为未展开、适用异常无结果、验收违反固定要求、正文冲突／关键行为存在影响结果的歧义，或无已确认来源／超出本版范围的内容被当成本版有效要求或验收，是产物不符合要求，记验证失败。明确标为拟议且未进入本版有效规格的建议不因尚未确认判失败；资料未取得、工具读取失败、用例错误或本次未核覆盖，记证据不完整。两者可并存，不能把已证实遗漏改称“待以后测试”，也不能把评价方没测到判为产品失败。

整份产物的通过须覆盖清单中的全部必要内容且评价有效；结构／链接通过、作者自检通过或部分需求通过都不足。本版必要行为／权限／验收仍有影响结果的未决项时，不能形成整份通过结论；已经明确行为、只待后续验证的假设按[PRD 方法第 4 节](../skills/prd.md#4-形成实际-prd)核条件和验证安排，不混作未定业务。报告完整字段沿[第 3 节](#3-执行事实结果与评价有效性)，PRD 部分关联完整产物清单及需求覆盖，之后才交用户作阶段决定。

发现问题先按共用根因规则定位原因和最小完整影响范围，交作者获准修正；未定业务交用户，不由评价方改稿代决。整改重测按第 4 节检查未解决问题、改变的需求／分支和有因果依据的关联验收／追踪；同一 PRD 文件不构成全稿重测理由。称为纯文字纠错的改动先比较实际差异，核行为、范围、验收、权限及追踪含义是否改变，再说明受影响核对／旧证据沿用依据；名称本身不能免检，语义改变则按实际影响重测。未受影响的首次证据有效才可沿用，覆盖有缺口不能以局部重测填成整稿通过。用户确认绑定实际版本，后续架构仍核独立授权。
