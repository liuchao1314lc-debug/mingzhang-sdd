# 需求暂存、澄清与变更

## 是什么、做什么、怎么做

暂存记录是沟通中的需求来源与确认记录，帮助避免遗漏；它不代替正式 MRD／PRD，不表示阶段通过。沿用目标项目已有记录载体；没有时使用 [组织提示](../assets/templates/requirements-record.md)，不建立额外管理服务。Agent 提取、回述、写入并核落点；用户决定要求、冲突取舍、收全及指定版本。

## 1. 边沟通边保存

核产品、阶段、当前请求和有效来源。MRD 澄清用户／问题、价值、范围和约束；PRD 把它细化为用户操作、产品响应、规则、异常与验收。澄清贯穿设计和开发：本层选择本层说明，改变上游行为／范围先反馈相应需求，不凭设计反改已确认要求。

用户可用不清楚、不精确的口语、示例或零散表达。转写时区分问题、需求、约束、用户提出的方案建议、假设与背景证据；用户提出的实现方案先回到待解决问题，未确认问题前不把方案写成需求。这一节是包内消歧与回述确认的唯一操作正文；messages、traceability 与各阶段方法只引用，不另写重复规则。任何专业转写、阶段交接包或正式成文前，先执行本段。

Agent 对影响结果的歧义或多种解释，先用大白话回述自己的具体理解及区别，由用户确认／纠正后再转写为本阶段专业内容；没有回应保持拟议。转写须保留已确认目标、范围、条件和预期，普通同义整理沿用有效确认，新增重要业务选择交用户决定，不能自行补成要求。选定含义与其适用范围立即保存；后续专业内容与选定含义不一致时回用户确认。

每项取得用户确认后立即保存稳定标识、具体内容、来源与确认依据、适用阶段／范围、状态和必要关联。尚未确认的理解、Agent 建议、假设、背景／证据、示例分别标识；没有反对和沉默不转成确认。记录完成后核真实落点，再向用户说已记下；写入失败就报告并保留当前消息，不假报保存。

按当前决策单元分批回述，频率见 [阶段沟通](../references/stage-methods.md)。持续向用户展示已确认、新增／变更、待决及冲突；可以引用未变项并展开变化，不反复让用户确认全部历史。

## 2. 改动与冲突

变更保留原内容、新内容、原因／来源、影响范围及用户实际确认。新要求与已确认项矛盾时，指出具体矛盾及后果，沿共用裁决规则给可行选择与推荐，用户决定；不能静默合并、删除或替用户选。依赖冲突的起草／实施等待，独立资料整理继续。

确认过的要求可变，旧决定保持历史身份，失效范围标清。同步对应记录、正式文档及直接关联追踪时沿实际许可，不为了统一措辞重写无关上游。

## 3. 收全后起草

新建 MRD／PRD 先基于记录分组展示本阶段全部事项，核遗漏、重复、冲突和取舍；事项较多时可按可独立验收的范围分批展示与收全，每批记录清单版本／范围／用户回应，最后汇总覆盖与遗漏，阶段级唯一收全确认不降低。只有用户明确确认“本阶段当前需求已收全”、影响起草的冲突已解决，才起草正式文档；单项确认不等于收全。收全依据须能唯一定位清单版本或具体事项集合、阶段／范围及用户实际回应，不要求固定口令；清单版本／范围标识、用户回应定位、适用阶段与之后变化在既有记录中可查。这一条件用于正式起草，不阻止之前记录和分析。

收全后又新增、删除或实质改变需求时，先留原清单与确认，标明旧收全依据不覆盖的变化，更新当前记录／版本。尚未确认的变化保持拟议；与现行要求冲突且影响继续的，暂停对应分支。变化经用户确认后，再展示变化及直接关联、遗漏／冲突核对结果，请用户确认本次变更范围已收全；未变部分沿用有效确认，不要求重答整份清单。用户一次回应明确确认变化内容及该范围收全即可，不另索固定口令或重复确认。纯文字纠错不改变含义时，说明依据，不使整份收全确认失效。

已有正式文档修订时，只对本次变更范围做同样核对并沿用其余有效确认；纯文字纠错及只读评审不重开需求收集。重要未定项限制依赖部分，不以接受风险替代业务决定。

已有正式稿时，把已确认变化标为“待同步正文”，在具备相应收全依据和写入许可后更新草稿，逐项核正文／验收及直接关联，再按 [评审返修规则](execution.md#10-评审意见返修与成果确认)取得所需版本结论。正文尚未同步或相关确认未更新时，指出受影响的旧条款／结论不能作为本次依赖判断依据；独立未变部分继续。变更内容确认、收全确认和正式稿通过仍是不同对象，不能相互代替；相应状态只能在实际动作／回应后更新。

## 4. 成文、检查与交接

按记录逐项核正式文档的具体落点，检查来源身份、含义、范围、异常／验收及确认是否一致，不能只核编号出现。未纳入项注明用户决定的理由；没有理由的遗漏先补齐，不能先说完成。需求记录与正式文档只维护关系，正式行为唯一在当前有效规格中。

关系建立／更新、交接与分析变化沿 [需求贯通方法](../references/traceability.md)；该方法唯一规范关系操作，本文件维护来源、确认和变更。交接精度按阶段要求展开，关键含义未定时明确受影响部分，不能让下一阶段猜测或从口语自行取舍。

收全确认、正式文档版本确认、真实效果验收与下一阶段许可分别登记。交接有效文档／版本、记录／决定依据、待验证假设与待决影响；恢复时读当前记录、变更及失效范围，不重问仍有效的决定。

## 5. 规则归属与开发前落点

涉及规则的需求，暂存时同时写明约束对象、归属层、唯一正文、当前有效版本和决定者：项目协作约定、目标产品行为与 Agent 工具动作分别归类。工具习惯不能直接成为产品需求，产品候选不能自动升级项目采用规则；同一来源跨两种身份时分别登记范围与固定对象，沿 [动作边界](core.md#三类约束与采用边界)处理。

产品详细规则在 PRD 落正常／异常行为及验收，架构／模块落系统与数据责任，组件落可实现契约，UI 落可见后果；上游交接包交可引用条目，开发建包时据此形成[实施进入条件](../references/stage-methods.md#实施进入条件)，不在上游正文另写下游合同。不要求首次开发前完成未来所有细节；关键业务未定只阻断受影响包，不能用技术探索结果倒填已确认需求。
