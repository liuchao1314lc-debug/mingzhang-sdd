# UI：用户能操作和理解的交互

## 是什么、做什么、怎么做

UI 把有效任务和组件状态转为用户可操作、能看懂的交互。根据真实通道选择图形界面、CLI、API 反馈或会话消息，不强制做页面。先流程、再状态／文案、低成本原型与任务演示、检查和交接；共用动作见 [阶段组织](../references/stage-methods.md)。

## 1. 输入、模式和责任

核 PRD 任务／验收、组件契约／状态、现有交互、目标用户与平台、本次设计／修订／只读范围。用户决定实际可用性反馈及指定版本，Agent 提方案、制作获准样例、观察与核对；不能把自己读懂记为用户读懂。

记录通道选择的用户任务／平台依据；采用非图形通道时说明为什么无需图形界面。交互条目关联需求／验收及组件契约，模块经组件追溯；不把 UI 链接填入模块／组件列冒充组件，不另建全项目覆盖表。风险与实际入口沿 [共用载体](../references/stage-methods.md#成果入口与验证载体)。

**本步落点与继续条件：**对象／平台／状态来源及许可进入 UI 记录；能定位当前用户任务后设计流程。

## 2. 先展示一条完整任务

梳理入口、必要选择／输入、操作顺序、完成与退出，说明每步用户看什么、做什么、产品回应什么。展示当前能判断的具体流程并请用户纠正，重要业务变化回 PRD；普通布局选择连续设计，不把内部实现细节放进用户决策。

**本步落点与继续条件：**流程与用户真实纠正进入 UI 草稿／记录；核入口到完成／退出连贯、必要行为决定已取得后做样例。

## 3. 可见状态、文案与原型

从组件真实状态映射加载／成功／失败、未执行／不足、取消与未知等适用表现；同时说明可用操作、数据后果、恢复路径及依据。未知不展示成功，不承诺撤回已发生动作。必要影响和决定实际呈现，详情可按需展开，链接不替代关键消息。

文案按 [大白话与 SCQR](../references/messages.md)，具体说对象事实、哪段未完成、接下来做什么；不要让用户先理解内部术语才回答。输入说明／错误指向能改的地方，按真实平台核相关可访问性。按任务和许可选择文字／流程样例、线框或可操作交互原型并标模拟身份，不因设计原型安装框架或实现生产系统。

**本步落点与继续条件：**状态／文案、组件关系和模拟样例进入 UI 既有位置；核操作后果及可见影响一致后演示。

## 4. 用户任务演示

给用户一个清楚、可信、中立的任务目标，说明演示对象／条件，再观察理解和操作困难；不以“请确认你看懂了”的引导式回答当效果证据。用户表示要求含糊时先改任务说明，再记录实际反馈与影响，不让用户猜检查词值。

有能力和许可时操作原型；只有文本交流就记录文本范围。Agent 纸面走查、用户文字理解、可操作演示和真实产品运行分别判断，不把未开展演示说通过。反馈按根因定位是提示、流程、状态还是上游行为，再修直接关联并核受影响任务。

**本步落点与继续条件：**真实任务说明、观察和用户反馈进入演示记录，模拟身份保持；困难未解决先改相关对象，已核可交付范围后评审。

## 5. 检查、完成与交接

实际核用户任务可走通、状态／操作后果与组件一致、关键提示已呈现、演示真实范围和反馈有落点，再依 [检查顺序](../rules/execution.md#9-检查动作与结论)报告。未操作的原型不能记操作通过；设计缺口具体说明影响。

静态截图只支持对应布局／文案表达检查，不能独自证明流程可操作、后台保存、权限或真实工具执行；这些结论分别需要相应操作与回执。

交指定 UI／样例、实际反馈、检查和未验证项，用户确认该版。获准后向 [开发](development.md)交流程、状态／文案、输入约束、组件关系及验收样例。UI 通过不等于产品验收／发布。无开发许可停止；恢复核现行任务、状态和反馈，不重做有效设计。
