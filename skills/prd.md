# PRD 成果方法

## 是什么、做什么、怎么做

PRD 把已确认的用户问题、目标和范围转成产品行为及验收，位于 MRD 之后、架构之前。交付能说明用户如何完成核心任务、异常后会发生什么、怎样判断结果的具体规格，支持起草、修订及只读评审。

按以下步骤核有效输入、展开行为、处理必要歧义、形成正文、自检、完整产物独立评价和交付。作者 Agent 形成成果并做内容自检，独立评价方按第 5.1 节评价完整产物，用户决定重要取舍与指定版本；模板、程序和本技能不代用户批准。执行前先完整读入口指定的共用规则、[需求记录](../rules/requirements.md)及[阶段沟通](../references/stage-methods.md)，通用操作不在此重写。

## 1. 接续与有效输入

核当前请求、目标项目／对象／版本、用户任务、允许动作，以及有效 MRD 或等效价值／范围依据、现有 PRD／需求／验收和实际决定。沿用既有确认；缺同名文档不重启 MRD。依据不足明确限制受影响判断；获准整理可把未知保留为假设／待决，不能写成已确认产品要求；正式起草还须满足需求记录的收全前置。

只读评审不写 PRD；修订只动相关正文及必要关联，保留编号、历史有效确认和无关工作。发现目标／价值改变先显化 MRD 影响；技术选型、模块分配和界面呈现留给后续设计，不在此借细化扩业务。

接续当前任务时，按 [必要检查选择](../references/checking.md#check-selection)确定本次要判断的对象、改动及实际验证，覆盖只读完成核对；所需修改前来源在首次相关写入前按 [原始采集步骤](../references/collection.md#collection-steps)准备。条件和成果版本按 [实际版本取证](../references/checking.md#version-evidence)取得，不能等改完才准备基准；没有本次动作的只读任务不制造写入链。

**本步落点与继续条件：**核对结果进入本轮记录，确认价值／范围足以支持当前任务后展开行为；缺口只限制对应任务。

## 2. 从用户任务展开具体行为

先定位 MRD 任务和实际用户结果，再写角色、触发／前置、输入、用户操作、产品响应、结果。核心任务必须真正展开，不能只写能力名单、页面、需求编号或指向另一方法。按一条任务分批向用户展示操作、响应与结果，关键理解确认后立即暂存；矛盾说明具体影响并由用户决定，变更保留原／新内容和确认。正常路径形成后，补相关空数据、权限不足、失败／取消／超时、重复与恢复的触发、可见结果、状态／数据影响及用户能做什么。

每项功能及适用非功能沿用稳定标识、记录来源、作用范围、优先级／理由、版本／确认状态及前置需求；示例不是默认业务。无来源建议保持拟议或删除。重要语义缺口按影响和不确定性就地标记，按共用规则的 PRD 材料范围整理；真实决定回写对应行为、异常与验收，不只留问答记录。独立可开展部分继续。

**本步落点与继续条件：**行为／异常理解在需求记录按任务暂存，核用户真实反馈和冲突后再细化验收；未收全不形成正式稿。

## 3. 验收与追踪

每项本版需求对应可判断的前置—事件—预期结果，指明观察对象、方法和证据；必要异常／权限分支不能只给成功条件。功能验收与长期价值观察分开，数量／指标从目标项目有效依据取得，不填通用默认阈值。业务对象、关系、术语及生命周期只补影响理解和验收的内容，不先设计数据库。

产品含模型行为时，按本项目实际任务定义允许资料／工具动作、确认／拒绝／撤回、结果核实、退出／接管、预算和不可信输入等相关行为及验收；真实模型／外部动作另核许可，不因定义评测而运行。已有真实失败按来源引用，没有就保持缺口。

在项目既有追踪位置连接来源任务／决定 → 具体需求 → 验收 → 计划验证。核首版任务是否漏项、需求是否有来源／验收、前置是否本版有效、异常及术语是否一致；模块、组件、实现和证据到实际形成时再登记。追踪只引用正文，不维护第二份完整需求。

**本步落点与继续条件：**把需求对应的验收、来源关系和必要假设记在当前分析／需求记录，核条件可观察及来源有效后准备收全展示。

## 4. 形成实际 PRD

先基于持续记录展示本阶段需求及行为／异常／验收，取得用户明确收全确认并解决影响起草的冲突后，再起草正式 PRD。已有文档变更只核受影响范围并沿用有效确认；确认绑定及后续变化统一沿 [需求记录第 3 节](../rules/requirements.md#3-收全后起草)，纯文字纠错和只读评审不重做收集。采用现有规格结构，必要时参考 [组织提示](../assets/templates/prd.md)。有写入许可才在目标项目写入并核后状态；候选、获准写入、实际写入和用户确认分别记录。新增内容能对应已确认目标及当前必要性，不能因模板有字段补业务。

在业务核心行为、异常结果、权限或验收尚未决定时，受影响部分保持待决；待验证假设要有对应需求、条件、验证阶段／责任和不符时处理。接受风险不能代替需求定义或动作许可。

**本步落点与继续条件：**正式 PRD 草稿写在项目已有规格位置，收全确认及记录关联可定位；所需改动取证依第 1 节在修改前准备，实际写入后保留动作及收尾原件，再做检查，不把候选当实际文件。

## 5. 检查、采用与内容自检

调用、只读收尾及执行前直读的分流沿 [必要检查选择](../references/checking.md#check-selection)。按第 1 节所选必要项实际调用并保留原始 stdout／退出事实，再逐项采用；只读核对 PRD 任务是否完成也执行适用的收尾检查，不能在看到必需成果缺失后直接省略程序采用。

对照第 1 节已选必要项，按真实来源分别确定各类 subject 并核业务 id 覆盖；验证对象及字段来源沿 [验证来源与绑定](../references/collection.md#verification-binding)，不把 PRD Ref 复用为全部检查的 subject。文件存在／可读结果不替代所需改动集合或实际验证结果，未调用的项不能写成已满足。输入版本不足时保留原回执，补获准的实际条件后只重做受影响检查。

逐项核回执身份／对象／条件及可采用性，再说明满足、缺口或不足怎样影响成果。检查顺序沿 [execution 第 9 节](../rules/execution.md#9-检查动作与结论)；对本方法第 2／3 节及确认记录逐项做语义核对，定位具体正文及未纳入理由；文件存在却只有能力名单、异常后结果未定义，都按核心未完成处理。确定缺口交回对应正文修正；事实／协议不足仅限制依赖判断，失败保留原始状态。Agent 的业务评审不改写程序执行事实，不以退出 0 代替阶段合格。

### 5.1 完整产物独立评价

完整稿形成并完成作者自检后、交用户确认阶段版本前，按[独立测试第 5 节](../rules/independent-testing.md#5-prd-阶段完整产物的独立评价)提交指定版本的完整产物和固定需求依据。完整范围、评价方独立性、逐项覆盖、人工核对／辅助命令、执行前原件保全、失败／证据不足及整改重测均沿该节，不另维护一份流程。

首次覆盖完整产物；后续澄清／整改及文字纠错的实际影响核对、受影响重测和旧证据沿用均按该节办理，不凭改动名称免检或重测全稿。既有通过版本不因方法增补重开。评价方或必要许可未落实时交准备材料并标独立评价未执行，不能由作者自己代签；部分产物可交付，但未完成独立覆盖不能宣称整稿独立通过。

## 6. 交付、确认与交接

按共用规则直接发送真实成果／版本、变化、作者自检、完整产物独立评价的覆盖／实际结论或未执行状态、未完成／未验证与影响、必要决定和接续输入；消息表达见 [用户提示](../references/messages.md)。缺口或部分失败也交已有成果，独立评价不能被自检替代。用户实际确认绑定指定版本，单独确认 PRD 不自动启动架构；若同一回复另授权下一步，分别登记范围。

可向后续架构交有效规格／确认依据、需求／验收、数据／权限／非功能／外部依赖行为及待验证风险；获准后按 [架构方法](architecture.md)接续，未获许可则停止。恢复核现行 PRD、变更及失效证据，不重问有效确认。当前结果在目标项目已有记录或交付中保存，不新建工作流服务。
