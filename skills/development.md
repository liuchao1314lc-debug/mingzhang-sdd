# 开发：逐功能实现与局部验证

## 是什么、做什么、怎么做

开发把有效规格／设计转成真实实现和局部证据。支持基础准备、功能／根因修复、仅计划及只读评审。按当前功能合同→计划／任务→实现→局部验证→符合性／质量评审→交接推进，不一次实现所有未来功能。共用动作见 [阶段组织](../references/stage-methods.md)。

## 1. 核输入与实际环境

核当前功能、有效需求／验收、相关架构／模块／组件／UI、现有源码／运行方式、工作区和许可；保留无关改动。Agent 编写、运行获准检查并报告，用户决定新范围、重要取舍和指定成果。源码不存在不代表技能必须有程序：文字资源承担方法，确定性动作确有必要才写代码。

基础准备先复用现有最小启动、测试和配置，只补当前实现缺口，不默认安装框架、CI、服务或新治理体系。运行、付费、私有资料外发、安装、Git 与发布核各自当前许可；不得把“启动开发”扩为所有外部动作。

上游尚未确认时，只在获准起草／探索范围形成注明身份的草稿；草稿或技能资源制作批准不等于目标功能通过。仅计划模式不实现、不运行测试。干净检出复现须在获准隔离位置进行，不清空当前工作区；未做时不能以本机可跑冒充干净环境可复现。

**本步落点与继续条件：**环境、工作区基准、有效输入与许可进入当前任务记录；能界定当前实现对象后计划，只有计划许可不写源码。

## 2. 明确一个功能合同和顺序

展示功能目标、范围／非目标、输入输出、异常及验收、重要假设和计划验证，确认新的重要方案后实施。沿既有文档保存合同／计划／任务／证据，小任务可合并载体；条件未定依赖项等待，独立工作继续。

制定测试方案须结合当前项目的实际需求、风险、技术条件和时间／成本约束，参考与测试对象相关的 [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)、[Google](https://testing.googleblog.com/2024/10/smurf-beyond-test-pyramid.html) 等官方成熟最佳实践建议，注明参考来源与适用理由，按项目实际选择方法、范围和用例；不照搬固定用例数、测试比例或工具流程，不以外部建议替代已确认需求与验收标准。

含模型行为的功能，计划时先按[第4节模型评测方法](#model-evaluation)确定需要的输入、预期、对象身份和执行条件；样例可以逐步落实，不能执行后才按实际输出补写预期。

任务按依赖排列，每项说明对象、动作、结果与实际检查；新建／修改／删除／重命名均核对应基准，不把全部脏文件排除导致漏掉本次改动。任务完成不能只看文件存在或编号打勾。

规划位置与实际入口沿 [成果登记](../references/stage-methods.md#成果入口与验证载体)区分；CODEMAP／等效地图只登记核实的实现，不为计划生成另一张实际职责地图。

**本步落点与继续条件：**合同／计划／任务保存于既有功能位置；核范围与验收清楚、必要决定已取得后按依赖实施。

## 3. 小范围实现与根因修复

按最小可检查增量实现本功能，随关键偏差报告具体事实和影响。问题按 [根因规则](../rules/execution.md#8-根因与修复)处理；先定位原因和最小完整影响范围，再选解决方案，不叠补丁／改标准凑绿。保留有效测试、用户工作及历史证据，不顺手重构无关区域。

实现中发现需求冲突，先指出有效规格与实际代码的差异，反馈受影响的需求／设计并取得必要决定，不以代码反批规格。试验成果进入正式实现须有采用依据与当前许可；试验成功、空实现、模拟返回或成功标签不能记为正式功能完成。

**本步落点与继续条件：**实际实现写在允许对象，任务记真实进度；重读写入结果并核改动范围后进入局部验证，未形成项保持未完成。

## 4. 实际局部验证和评审

依据改动运行必要测试／检查，先取得原始结果再核是否命中目标分支，按 [检查顺序](../rules/execution.md#9-检查动作与结论)下结论。有意义的缺陷回归应能识别修复前错误，修复后成立；纯低影响文字改动用内容／关系核对，不写镜像实现的测试。

先核规格符合性，再核相关维护／质量风险。失败保留原结果并定位修复，重核受影响项；必要检查通过后，除新变动／失败／疑虑外不机械反复全量运行。替身与真实依赖、静态内容与模型效果分开。

<a id="model-evaluation"></a>

产品确有模型行为时，Agent 将有效验证策略落实为可复核的评测材料与结果，按以下顺序做；普通软件不因使用编程 Agent 而自动增加模型评测：

1. 从已确认要求选本功能必要的正常、相关失败与禁止情形，先写每个样例的输入／前置、允许动作、预期结果及判断依据。预期来自有效规格，不从待测输出或厂商默认评分反推；重要行为歧义先交用户决定。
2. 在既有计划／证据位置固定实际模型、提示、工具／配置、相关数据及样例的版本或可恢复副本身份，关联具体预期。两版比较使用共同请求、条件和判据，注明真正改变的对象；不强制评测平台或每项重新做哈希。核当前调用／资料许可、时间／费用上限及可取得的回执，不足则只准备材料。
3. 获准后执行，保存逐样例真实输出、相关工具调用／返回、执行状态及对象身份；替身与真实分开。超时或未知结果先核原动作，未取得证据不填成功，不用退出码或代码测试替代模型任务判断。
4. 对照预先固定的结果与禁止情形逐项判断，记录满足、偏差或证据不足及理由，明确样本／条件限制。结果或预算未明不签整体通过；改变模型、提示、工具或样例后按实际影响复查，不把少量通过扩成未测行为或长期收益。

原始结果和分项判断沿既有证据位置交接，用户按指定成果确认；明确安排独立评价时再沿下述独立规则，不由本方法自动增加评价方或模型调用。

明确安排独立测试时，评价方按 [独立测试规则](../rules/independent-testing.md)从固定要求自行设计；Agent 开发者的局部测试仍是自检。交评价方有效要求／禁止情形、被测版本、运行条件及许可，自己的测试结果只标补充；获准整改后按因果影响交独立重测，不默认让本实现者代签独立评价。

**本步落点与继续条件：**原始结果与分项采用进入既有证据位置，符合性／质量意见引用实际对象；必要缺口先修正再复查，核验完成后交付。

## 5. 交付、停止与联调交接

交实际实现位置／版本、本功能变化、局部结果及原始证据、未完成／未验证、运行方式及必要风险；不能把局部通过写成系统／用户验收。用户按实际范围确认成果，提交不默认发生。

获准后向 [联调测试](integration-testing.md)交确定实现／环境、系统任务与验收、依赖／替身限制、缺陷和有效局部证据。无联调许可停止。恢复核工作区／版本、任务和未知动作状态，先核原结果，不盲目重跑副作用。
