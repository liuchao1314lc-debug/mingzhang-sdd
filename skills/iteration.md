# 迭代：依据真实反馈选择变更

## 是什么、做什么、怎么做

迭代从有来源的反馈或已知缺口选择本轮改进，并接续受影响阶段。支持反馈／计划、已确认变更实施及只读评审；产品尚未发布也可处理开发反馈。按事实→根因／影响→优先取舍→选择接续层→验证／再观察推进，不机械重跑十阶段。共用动作见 [阶段组织](../references/stage-methods.md)。

## 1. 核反馈与当前版本

核现行需求／实现／发布身份、反馈来源／时间、反馈渠道与责任人、预期与实际、复现条件及已有证据。多条反馈先按问题归类去重，标来源／角色／频次或影响面、证据强度，列本轮候选全集及纳入／暂缓理由；无统计时用可核实的手工计数，不编数字。Agent 整理与分析，用户决定优先级、本轮范围和重要取舍；未上线不编用户使用统计。意见、观察、假设和已证实问题分开，沿 [需求记录](../rules/requirements.md)保存确认与变化。

**本步落点与继续条件：**反馈及确认进入既有问题／需求记录，核版本和事实来源后分析；未知条件先补证。

## 2. 根因、影响和候选方案

首次分析反馈影响前，先读 [需求贯通方法](../references/traceability.md)。沿已有关系把反馈及原问题证据关联到具体原需求、价值目标和有效变更；已有项目无 MRD 时引用经确认的等效依据，不补造历史。新想法尚无原需求时如实标明候选，按需求规则澄清确认，不假作既有缺陷。

按 [根因规则](../rules/execution.md#8-根因与修复)判是缺陷、交互困难、新需求或架构限制，调查必要关联，确定最小完整范围。来源不足先补证，不拿用户一句建议直接扩功能。

比较用户影响、价值、风险、成本和依赖，给本轮纳入／暂缓及理由，不编默认分数；优先级比较使用可核依据并单列需用户决定项。弃用／sunset须写对象、替代、迁移、通知、旧版本支持窗口与回滚，不自动删除能力。向用户展示当前问题、候选方案、改变什么及保留什么，取得新范围／重要取舍确认后实施；尚未决定依赖部分等待，独立整理继续。

本轮需要观察用户效果时，在选方案时同步按[第4节效果观察方法](#outcome-observation)核成功依据、证据条件和所需许可，不等改完才决定如何证明改善。

安全、权限、关键流程与数据问题明确实际风险，不静默降为以后优化；变更涉及必要行为／权限／验收时先取得相应决定，暂缓标签不替代本版完成条件。

**本步落点与继续条件：**候选方案及用户纳入／暂缓决定进入迭代记录；确认本轮范围后接续相关层。

## 3. 选择受影响阶段接续

用户／问题／价值或范围改变回 [MRD](mrd.md)；产品行为、规则或验收改变回 [PRD](prd.md)；系统机制改变回 [架构](architecture.md)，责任／接口分别接续模块／组件，交互问题接续 UI，已定行为的局部缺陷进入开发。必要关联层同步，未受影响的有效确认不重开。

变更保留原要求、新内容、原因和确认，沿实际消费关系定位受影响的具体设计、任务、实现、用例和证据，说明哪些仍有效、待重核或已失效及原因；不只改关系线后沿用旧通过。重要新需求按对应阶段收集与起草规则处理，不绕过确认门槛。实施在当前许可内按 [开发](development.md)和 [联调](integration-testing.md)接续，阶段版本确认与动作许可分开。

**本步落点与继续条件：**在所属阶段正文同步已确认变更，迭代记录仅引用关系；核直接关联和失效范围清楚后实施／验证。

## 4. 验证与再观察

制定测试方案须结合当前项目的实际需求、风险、技术条件和时间／成本约束，参考与测试对象相关的 [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)、[Google](https://testing.googleblog.com/2024/10/smurf-beyond-test-pyramid.html) 等官方成熟最佳实践建议，注明参考来源与适用理由，按项目实际选择方法、范围和用例；不照搬固定用例数、测试比例或工具流程，不以外部建议替代已确认需求与验收标准。

实际检查改动是否解决原问题、相关旧能力是否仍成立，沿有效标准与适用证据，不依据结果修改成功线。按 [检查顺序](../rules/execution.md#9-检查动作与结论)核完再给结论；测试通过不能代替用户效果改善，计划的长期观察标计划。

已有或新获准的独立评价按 [独立测试规则](../rules/independent-testing.md)接续（触发与交接索引见该规则开头）：依据已固定的本轮要求，先解释哪些实际结果会受变更影响，再定重测范围／命令、留原始副本；不因属于同一模块而重测整包，也不由独立通过推定新版本或下一轮已获准。

<a id="outcome-observation"></a>

本轮改变用户效果或需要后续观察时，Agent 按以下顺序承接 MRD／经确认等效依据的成功观察：

1. 引用现行 MRD 或经确认等效依据中的价值目标、观察方法／标准及原问题证据，说明本次改变什么、哪些结果可能受影响；不另定指标或按回归结果修改成功线。缺有效成功依据时回相应层澄清，已有明确依据不重问。
2. 在既有迭代记录安排观察什么、由谁取得证据、使用哪个版本／场景、在什么条件或时点观察、记录在哪里及需要什么许可／成本；负责人须具备条件或取得其确认，不能单方面给用户安排任务。已有成功观察安排适用时直接引用，只补本轮变化；重要取舍由用户决定，缺许可保持计划，独立实现／检查可以继续。
3. 按实际获准安排取得证据，记录真实结果、原始来源和样本／局限，对照原问题及成功依据分析改善、无改善或证据不足。原基线未知就报告未知，不补造比较；未取得证据保留“实现／相关验证结果已形成，效果未验证”的分项状态，不主动新增付费调用、监控或定时任务。
4. 根据结果提出继续、调整或停止的建议与理由，交用户决定新的范围／重要取舍；证据不足交接具体未完条件和已有材料，不自动执行下一轮。效果观察是本轮变更到后续决定的依据，不以测试通过替代用户收益。

**本步落点与继续条件：**实际结果及真实后续反馈进入既有证据位置；尚无用户效果证据保留未验证，按实际完成范围交付。

## 5. 完成、交接与恢复

交本轮确认范围、实际变化、验证／真实反馈、原目标与受影响关系、暂缓理由和剩余问题；所有暂缓项保留接续层与进入条件；仅在范围、行为未定或改变时要求澄清，并沿用已有决定，不能只给暂缓标签；这些材料及现行规格／实现版本作为下一轮交接输入，正文与关系沿已有位置维护，不另建台账。用户确认指定成果后按当前许可交付，下一轮另核实际请求。归档只整理真实记录，不自动删除／重置旧成果。停止在授权止点；恢复读现行版本、确认与未完事项，不把旧反馈当最新事实。

交接给受影响阶段或下一轮的交接包按[阶段交接物格式](../references/stage-methods.md#阶段交接物格式)组织：反馈、现行版本与确认、原需求／原问题关系、变更范围、接续层、验证／观察结果、暂缓理由与剩余问题、下一层输入及路径引用。其余通用字段、五类状态与模板沿格式节。

## 6. 规则、历史与采用的接续

先按 [三类约束](../rules/core.md#三类约束与采用边界)判变化影响产品规则、项目约定还是 Agent 工具行为，回唯一责任层修订并交相应决定者；只改产品候选不自动替换当前采用的执行规则。交付新固定对象及变化范围，原确认留在原对象，新版内容确认与新版采用分别登记。

历史与当前摘要沿 [当前摘要与历史](../references/project-governance.md#当前摘要与历史)对账，保留生命周期及保存身份；历史操作与升版判定沿该文“历史文件操作入口”“项目版本计划与升版判定”；封存、未提交或有意排除不得改称已入库归档。只重开受影响范围，开发第 2 节的包／路线／并行安排在当前合同内承接，不由归档动作开启下一轮或分发。

本次版本变更的文件引用、同步／复核、局部取代和源码／制品对账沿[项目资料与版本治理](../references/project-governance.md#project-material-version-governance)，在既有变更与交付记录关联原基线、新对象和直接消费者；上游再变或对象身份漂移时，只重核受影响的依赖与确认，不将旧结论换绑。交接前按该方法核入口和现行指针，副本同步、迁移清理及发布仍须各自许可，不借治理启动下一轮动作。

**成果最小清单（完成前核对）：** ①反馈来源与分诊；②根因／影响／证据；③候选与优先级依据；④本轮范围与接续阶段；⑤验证／观察结果；⑥未采纳／暂缓理由、接续层与进入条件；⑦下一轮输入；弃用／迁移（如适用）。缺①③④标缺口，不默认记本轮范围成立。
