# 模块：职责与协作

## 是什么、做什么、怎么做

模块是系统内有明确职责的逻辑边界；不必等于目录、服务或 Agent。把有效架构细化为职责、状态归属、依赖与协作，使一个当前任务能跨模块完成。先读 [阶段组织](../references/stage-methods.md)，用实际任务走查设计。

## 1. 输入、模式与责任

核有效 PRD／验收、架构／决定／系统验证策略、现有模块和本次新建／修订／只读范围。Agent 提取责任、设计协作并核覆盖；用户决定影响范围或责任的重要取舍及指定版。关键架构未定时标依赖，不用模块反推产品要求。

风险／试验、规划与实际入口、唯一追踪均沿 [成果载体](../references/stage-methods.md#成果入口与验证载体)，注明受影响模块；无有效风险载体时交待验证事项及影响，不另造模块风险记录。设计形成不预填代码、测试或用户通过。

**本步落点与继续条件：**输入／版本及本轮任务进入模块记录；当前链路与架构边界足够明确后划责任。

## 2. 划分职责与状态

按业务任务和失败责任定当前需要的模块，给稳定标识、职责／边界、需求依据及架构对应；共享责任说明必要性，不先设计全部未来模块。适用非功能明确谁实现、谁协作、谁汇合判断，不只放整节链接。

对关键数据／状态明确权威、读写者、产生／改变时机及交接，不多处维护当前状态。向用户展示当前任务如何分工，争议决定后再依赖它细化；正常分工内连续推进。

**本步落点与继续条件：**模块条目和状态归属写在模块稿；核需求归属及权威不冲突、影响分工的决定已取得后细化协作。

## 3. 依赖与协作契约

明确工作发起方向与被依赖职责；返回／向上请求单独说明与主发起图关系，不误当循环或静默漏边。发现循环定位实际原因，必要时调整责任／契约，不用新增中间层遮盖问题。

每个必要协作给调用条件、输入来源、输出／负责人、异常／超时／取消／未知、权限和必要资源约束，引用架构唯一接口。宿主读取即可确定的事实直接取证，需要分项判定或明确程序回执时才起检查程序；一次读取不冒充程序调用。

**本步落点与继续条件：**依赖关系和接口引用进入模块稿；核发起／返回及必要输入输出可连通后走查。

## 4. 当前端到端任务走查

依当前授权选择代表任务，说明为何能验证关键责任；选择影响范围时先给用户建议。逐节点核发起者、输入、协作、状态／异常与汇合结果，记录具体模块落点，覆盖正常及相关缺失／失败分支；声明的分支必须实际走到。

这是设计走查，不能说真实执行通过。核覆盖关系双向一致、接口只有唯一依据、过关条件能定位到正文；按 [检查顺序](../rules/execution.md#9-检查动作与结论)核完再报，缺项按根因规则修正。

**本步落点与继续条件：**在模块稿保存实际走查节点与缺口，核所声明分支均有落点；关键职责未闭合先修正，闭合后交付指定稿。

## 5. 完成与组件交接

交模块职责、数据权威、依赖／协作及实际走查结论和限制，用户确认指定版本。获准后向 [组件](component.md)交当前功能、所属模块、唯一接口依据、异常责任与系统策略；仍有内容前置明确限制。未获后续许可停止，不建源码／安装。恢复沿当前模块和受影响任务，不因改版重划全部责任。
