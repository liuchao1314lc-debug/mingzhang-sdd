# 联调测试：系统任务、缺陷回归与用户验收

## 是什么、做什么、怎么做

联调测试检验指定实现与实际依赖能否完成系统任务，并组织用户验收。支持计划／准备、执行／回归、只读评审和获准交付；实际发布单独核许可。按环境与对象→任务覆盖→执行→缺陷归因修复回归→验收→获准交付推进，共用动作见 [阶段组织](../references/stage-methods.md)。

## 1. 输入、许可与责任

核代码／构件版本、环境、运行方式、有效规格／验收、系统验证策略及局部证据；确认真实依赖、资料、账号、费用和动作许可。Agent 组织并执行获准验证，用户作指定版本验收及发布决定；仅计划模式不执行真实调用。

缺环境或许可只限制相关测试，说明缺口和独立工作；不把替身换成真实依赖却沿用旧批准，也不以不可复算状态说已通过。

**本步落点与继续条件：**指定版本／环境、已有证据和许可进入验证记录；关键前置具备才执行对应任务，未具备时仅准备或报告。

## 2. 准备系统覆盖与用例

首次准备系统覆盖及用例前，先读 [需求贯通方法](../references/traceability.md)，沿现有关系定位本轮系统任务实际承接的具体要求、有效验收及实现对象。

制定测试方案须结合当前项目的实际需求、风险、技术条件和时间／成本约束，参考与测试对象相关的 [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)、[Google](https://testing.googleblog.com/2024/10/smurf-beyond-test-pyramid.html) 等官方成熟最佳实践建议，注明参考来源与适用理由，按项目实际选择方法、范围和用例；不照搬固定用例数、测试比例或工具流程，不以外部建议替代已确认需求与验收标准。

系统测试计划同时写本轮验收／发布阻断条件：引用有效验收或用户本次决定，未定项标待决及影响，不设通用阈值；结论按该条件对照。从用户任务串联真实边界和结果，复用有效局部证据，覆盖关键正常、相关失败／权限／取消／未知及适用非功能。每项用例关联具体要求／验收、系统任务及受测实现／接口，标前置、数据／依赖、步骤、预期与观察位置；沿来源核预期保留原目标，不从待测输出反推标准。计划与执行记录分开，不另造评分体系或默认重跑全部。

涉及运行、部署、升级或迁移的任务，先引用[架构的运行与恢复交接](architecture.md#runtime-delivery)，核指定版本的机制、前置和当前环境是否匹配；机制未定回架构补齐，环境或许可不足只暂停受影响操作，不到执行时临时猜恢复办法。

先向用户说明实际版本、测试范围、真实与替身、重要缺口及影响；取得必要新决定后执行。公开示例／假数据需标身份，不能证明真实用户结果。使用真实账号或生产数据时，另记来源、是否含真实用户资料、脱敏与清理责任人、许可；适用项由用户决定，不替代法律或平台审核。

按适用补系统级非功能验证（性能、安全、无障碍、兼容、恢复）；升级／迁移／回滚验证旧数据、旧版本与回退，不只新装。发布前形成发布说明（版本、变更、已知问题、回滚方式、支持入口）与发布后 smoke／监控计划（指标、日志、告警、责任人）；未执行标未验证。

系统测试不自动成为独立测试。用户明确安排独立评价时，按 [独立测试规则](../rules/independent-testing.md)固定本任务全部可测试行为、准确命令和原始文件保全（触发与交接索引见该规则开头）；引用系统策略不等于纳入该策略全部内容，不默认增加测试层或门禁。

**本步落点与继续条件：**用例与计划沿现有系统验证位置维护；核条件、标准和许可足够后执行，不拿计划当结果。

## 3. 执行、缺陷与回归

实际执行后保存原始输出、环境／版本、执行状态和观察结果，将证据关联实际用例、真正受测对象及所核的具体要求，核检查生效，再判任务是否满足；模型／随机行为引用开发评测在执行前固定的重复、预算与容差；统计性结论不凭单次结果，但一次即可确认明确违反有效要求的行为直接按违规／缺陷报告，不被重复统计掩盖；失败、未测、不适用与证据不足分开。发现缺陷及时报影响，关联违反的有效要求、预期／实际及原始证据，按 [根因规则](../rules/execution.md#8-根因与修复)定位环境、实现、接口还是规格，再回相关责任修复。

修复后核原失败任务和有因果依据的直接受影响要求／用例，保留原缺陷、修复对象与新结果的关系，不改预期来凑通过。超时／未知先核原动作状态，不能自动重跑外部写入或付费任务。检查有效性、版本身份和实际采用按 [检查顺序](../rules/execution.md#9-检查动作与结论)执行。

独立评价的整改重测由该规则裁剪到未解决／改变行为和有因果依据的回归；测试本身出错保留证据不完整，不能覆盖原始文件后改成产品通过。独立验证结论、系统结果和用户验收各按真实范围报告。

安全、权限或关键流程缺陷须说明实际影响，不能静默归为以后优化；涉及范围／权限／验收变化先取得对应决定，一般风险接受不替代必要行为或有效标准。

**本步落点与继续条件：**原始结果、缺陷及修复／回归关联进入既有验证记录；关键失败未解决不宣称系统合格，核完实际范围后进入用户验收。

## 4. 用户验收与获准交付

向用户展示指定版本的实际任务结果、证据与限制，明确请验收的范围，记录用户真实回应；Agent 自检／系统测试不代签。尚未执行用户验收保持未验收，不把文档已交付称产品接受。识别指定验收者、发布批准人、平台／部署操作人；验收结论与发布许可分别核对，对话者确认不代替有权决定者。

发布准备形成发布就绪清单：对象／版本、平台与账号、提交材料、审核状态（提交／审核中／通过／驳回重提／发布或未发布）、审核窗口、回滚／停止条件、责任人；登记发布后反馈渠道与责任人。线上故障按“报告事实／影响→有权者决定止血或停用→最小修复并保留证据→事后补需求／评审”处理，不擅自回滚用户数据，不新增阶段。

平台有官方规则时，验收前核架构固定的平台约束落实；发布前按届时有效规则复核，留下来源／版本日期、复核结果及变化影响，旧核查记录不能代替。

当前请求包含发布时，依据指定架构的[运行与恢复交接](architecture.md#runtime-delivery)备好可审的构件、目标环境、操作范围和发布后检查方案，再取得实际发布许可并执行；已有明确许可沿用。发布后对照该依据核正常／停止条件，失败由明确承担者按获准处置处理，不擅自回滚用户数据；记录真实结果与限制，不能因方案存在就判恢复成功。仅交付本地文件不声称线上发布。

**本步落点与继续条件：**指定版本用户回应、发布许可／操作及真实结果分别进入现有交付记录；未取得或未执行就保留相应状态，不能借上一项确认补下一项。

## 5. 完成与迭代交接

交系统结果、对应要求／受测对象／用例／证据关系、指定用户结论、已知缺陷与影响、发布事实或未发布状态、操作／恢复限制。获得后续许可后向 [迭代](iteration.md)交版本、真实反馈、问题／证据及其原要求关系与未验证项。阶段结论不启动定时监控或新任务；恢复核现行版本、环境、未知动作和失效证据再接续。

交接给迭代的交接包按[阶段交接物格式](../references/stage-methods.md#阶段交接物格式)组织：实现版本、验收与许可、系统结果、用户验收结论、发布事实或未发布状态、缺陷与未验证、迭代输入及路径引用；未验收／未发布也可按许可交反馈分析。其余通用字段、五类状态与模板沿格式节。

**成果最小清单（完成前核对）：** ①受测版本／环境／用例与覆盖；②原始结果与缺陷回归；③指定验收者与用户验收结论；④非功能／平台／迁移／回滚（按适用）；⑤发布就绪与审核状态（如发布）、发布说明与发布后监控计划；⑥反馈／故障／限制；⑦迭代交接。缺②③标缺口，不默认记系统合格。
