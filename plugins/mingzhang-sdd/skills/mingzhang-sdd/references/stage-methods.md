# 阶段方法结构与沟通粒度

## 方法怎样组织

每份方法实质回答是什么／做什么／怎么做，进一步写明模式与裁剪、有效输入／进入条件、人和 Agent 分工、有依赖的动作及沟通、输出与检查、异常／变更、完成条件、交接及停止／恢复。小任务可以合并表达，不能用标题齐全代替具体操作。成本、资源、隐私、外部依赖、迁移与兼容仅在影响本阶段时展开。

每步要能判断：依据是否足够、谁做什么、什么时候沟通或等待、成果落在哪里和是什么状态、怎么实际检查、检查后继续还是修正。共用动作引用 [execution](../rules/execution.md)；需求记录引用 [requirements](../rules/requirements.md)，每阶段只维护自己的动作、节点与内容判据。

阶段方法中的资料核对、分析、写稿及检查动作默认由 Agent 执行，用户决定的节点明确指出。任务模式优先于步骤落点，完整只读边界见 [core](../rules/core.md#只读模式与步骤权限)。以下文件落点仅用于具有相应写入许可的模式：分析／设计写在项目既有对应阶段稿，状态写在既有状态／交付记录；没有载体时只补本次必需位置。MRD／PRD 在收全确认前只写需求记录和分析材料，不写正式稿。每个节点形成后回查其输入、具体成果和下一步前置，关键决定未取得则只停依赖部分，不让“先写完后再确认”倒置顺序。

用户负责目标、优先取舍、重要范围／设计决定及指定版本批准；Agent 负责核输入、提供理由清楚的方案、执行获准工作、检查与准确报告。真实用户验收不得由 Agent 自检代签。用户新决定要回写相应正文／记录，已有授权内普通工作继续。

## 成果入口与验证载体

规划、缺失和实际形成的成果分别登记。计划路径只放计划／任务并注明规划，未形成不预填实现、验证或批准；CODEMAP／等效地图只登记核实的实际入口，已有载体优先，不为设计阶段另建代码地图。模块／组件设计形成不等于代码实现。

架构统一维护或引用系统验证策略及风险／隔离试验载体，模块、组件与 UI 只关联本层受影响事项，不另建风险系统／台账或评分体系。没有有效载体时交待验证问题、影响与所需决定；试验执行另核许可。需求—模块／组件关系沿项目唯一追踪入口，各层条目反向引用；实现—任务／证据表不再重复维护同一模块／组件关系。

复用或精简来源时，核对本次实际采用的正文及适用条件，把会改变执行、判断或交接的条件落到相应步骤或有效共用引用。入口、标题、编号齐全不能证明承接充分；未承接部分说明影响，不能用未来验证计划补成当前核心行为已明确。普通动作授权不替代步骤前置成果与核验。

## 按阶段沟通

不设通用次数或每操作审批。围绕用户当前能判断的事项分批展示；重要理解或选择影响后续动作时先沟通，普通进展说明具体结果和下一步。表达按 [大白话与 SCQR](messages.md)，不要把内部字段直接当用户问题。

| 阶段 | 主要沟通单元 | 应展示和需要用户决定的节点 |
| --- | --- | --- |
| 启动准备 | 目标、已有项目现状和本次许可 | 回述要做的事、可复用资料、缺口、准备成果和后续范围 |
| MRD | 一个用户问题／场景及预期效果 | 连续展示当前需求、纠正理解、冲突与首版取舍；收全后才起草 |
| PRD | 一条用户任务及相关正常／异常结果 | 展示实际操作与结果、规则和验收；逐批确认并暂存，收全后起草 |
| 架构 | 端到端链路及影响目标的技术取舍 | 方案理由、关键风险与验证限制；先确认重要选择再据此展开 |
| 模块 | 一段协作任务及职责交接 | 谁负责、传什么、失败归谁处理；确认影响分工的争议 |
| 组件 | 一个当前功能的接口／状态分支 | 输入输出、异常／未知后果、替身边界；不向用户抛每个内部字段 |
| UI | 一个可完成的任务及可见样例 | 让用户看实际措辞／原型并演示任务，记录真实理解和困难 |
| 开发 | 开发包批次或完整候选版本 | 按开发方法第 2 节展示包清单、依赖路线与并行条件；合并评审回执并保留逐条理由，及时呈现必要裁决；交包成果、局部证据和未完成项 |
| 联调测试 | 一个系统任务／缺陷和验收版本 | 环境与实际结果、修复回归、用户验收及独立发布决定 |
| 迭代 | 一个有来源的反馈及候选改进 | 问题证据、影响、优先级与本轮范围；确认取舍后接续受影响阶段 |

同一节点不因更新文件而重问；阶段切换、重要变更和待决按共用触发呈现。完成后交指定成果与真实检查，停止在当前授权边界；恢复读当前对象／版本、决定及未完成事实，不把历史证据当本次执行。

## 评审返修与交接

十阶段共同沿 [execution 第 10 节](../rules/execution.md#10-评审意见返修与成果确认)处理意见、返回受影响步骤、实际复查和核指定成果结论；各方法中的检查／交付节点按该流程收口，不另维护十份返修规则。必要缺口未消除时可交已有成果及限制，但保持受影响任务未完成；用户评审结论与下一阶段许可分别核对。需求变化涉及收全／版本确认时同时沿 [requirements 第 3 节](../rules/requirements.md#3-收全后起草)处理，只重核受影响范围。

## 规则职责与采用

[三类约束](../rules/core.md#三类约束与采用边界)按约束对象及采用身份定位，不按目录或文件名判效力。项目既有采用索引维护唯一来源、适用条款、固定提交／blob、实际决定、责任人与回退；若用结构化登记，索引只作指针，须逐条核身份与引用一致，不能并存两个采用权威。产品运行资源可独立交付，不依赖作者项目台账。

用户决定产品目标、重要规则／取舍、项目约定及指定版本；Agent 提出方案、维护获准正文、执行与自检；宿主约束实际工具权限。实施者身份须来自实际任务／委派，独立评价方须另核来源、独立性、范围及许可，不从“审计方”称谓或开发者自检推定已经落实。冲突回规则所属责任层，相关动作等待，已有明确许可内的独立部分继续。

## 实施进入条件

本“实施进入条件”小节是 [development.md §2](../skills/development.md#2-明确一个功能合同和顺序)合同字段清单的补充，经该文文首“共用动作见 阶段组织”承接；Agent 在同一既有合同内补出本小节，不另建合同、模板或台账。

两层前置：PRD—UI 先按层完成当前范围的行为、系统／模块责任、契约与交互；每个当前开发包在既有合同的“实施进入条件”小节逐项引用下列落点。Agent 核对，重要缺口交用户决定，不以口头自检或标题打勾代替：

1. 有效需求／设计标识、固定版本和范围，能追溯到实际确认。
2. 正常及相关异常结果、权限和数据后果；具体正文分别在 PRD、组件与 UI。
3. 实现执行者、接口／状态权威及失败处理负责人，职责与许可可核。
4. 验收与验证依据、可观察结果及实际可用验证入口，计划和证据分开。
5. 未决项、受影响包、解除条件及可进入／等待判断；关键业务未定只停依赖包。

组件与 UI 负责对应输入交接，开发方法负责包／路线和执行；技术探索注明假设、范围、许可及结果，不计正式包完成。无需在首次开发前定完未来全部细节。已授权设计／候选制作不等于指定设计版本通过，进入依赖实施仍核实际前置。

人工交接核对不伪造程序回执；实际调用确定性检查时才沿[检查合同第 3 节](check-contract.md#3-回执与两轴)保存两轴及原始返回，退出 0 不代用户签认。沿现有合同和状态即可，不强制新增模板、台账或工具。

## 当前摘要与历史

当前入口和运行文件只维护对象身份、适用范围与采用／结果指针；提交与核验的当前状态只在目标项目既有当前状态区（追加式 STATUS 为末节）及既有证据的固定对象结果节维护，其余文件不得复述。历史记录和原始结果保留原对象，不用时点标签把失真的句子继续当当前说明。检查具名状态落点的对象绑定指针及有无失实状态自述，方法正文中的规则、类别与示例不作为项目当前状态扫描；程序不能判任意语义或替用户批准。

内容生命周期（草稿、当前、已替代、封存、历史证据）与保存身份（已提交、已跟踪未提交、未跟踪、有意排除）分别记在项目已有权威索引及状态，文件自述只引用；规则的变更／采用依据随对应决定记录，历史批准只绑原对象。STATUS 行号及数量注明提交或工作树观察版本，不能统一偏移换算；目录存在、原位保存、入库归档分别判断。

## 项目资料与版本治理

本方法用于目标项目各阶段的资料整理、版本交接和获准交付。沿已有文档、合同和记录维护，不要求固定文件名、目录、登记 schema 或新台账；只读模式只报告建议落点。Agent 在授权内起草、维护、核对并报告，用户决定重要职责／范围／兼容取舍及指定版本，独立评价和发布责任按实际安排登记，不从文件存在或角色称谓推定委派。

### 文件与信息

先明确每份文件的主要职责、唯一正文、维护者和需要谁决定；小项目可在已有文件中用具名分区隔离职责，不为分层强制拆文件。职责与更新触发如下，更新均受当前写入许可约束：

| 资料角色 | 保存内容与边界 | 更新触发 |
| --- | --- | --- |
| 稳定定义与规则 | 产品定义、长期约束及专题机制；不记录每轮进度 | 对应有效决定或机制变化 |
| 当前事实与职责入口 | 当前任务、风险、下一步及已核实的实际职责；状态与地图分别维护自己的内容 | 事实、实际入口变化或交接 |
| 功能合同 | 当前功能／开发包的范围、输入、交付及验收依据 | 该功能范围、前置或契约变化 |
| 专题合同 | 跨功能复用的领域机制及边界；功能合同引用，不复制 | 该专题机制或责任变化 |
| 历史证据 | 原对象、当时决定、实际执行及结果；不充当当前任务清单 | 结束或被替代时建立索引；更正用接续记录，保留原件 |

约束对象决定[三类约束](../rules/core.md#三类约束与采用边界)的权威正文和归属，资料职责决定该文件／分区的角色；不能因为都叫“规则”就放入工具约束目录。稳定规则的来源、适用范围与实际采用关系沿“规则职责与采用”，当前授权／状态及固定结果沿“当前摘要与历史”，导航和摘要只指向它们；正文之间的冲突沿[core 的裁决边界](../rules/core.md#资料身份与冲突裁决)，不按文件名选赢家。存在结构化登记时，按文件逐项核正文指针所列键与该登记对应键集相等、无重复，不合并不同文件的键来掩盖缺项；项目未使用登记时不为此创建 schema。

接手从目标项目真实宿主入口开始，依次定位当前请求及许可、生效规则、当前阶段的有效规格／合同、实际成果与所需证据，再按任务查历史；沿已有阅读路线，不固定重建一套根文档。来源是示例、提案、外部反馈、原始观察还是有效决定须保持身份；日志／记忆和读取受阻的处理沿 core，不能用宿主摘要替代完整方法或正式授权。

历史文件中的“当前／下一步／必须做”仅属其当时对象和范围；在既有索引标明历史身份、适用对象、取代依据及现行入口，不回改旧批准或原始结果。部分条款／字段仍有效时逐项说明，只替代失效部分，不整份判废。生命周期与保存身份直接引用“当前摘要与历史”，不另定义；原位保存、入库归档和排除登记不能互相冒充。

源码、生成目录、分发制品、安装副本、外部公开树分别注明实际来源／版本、用途和核对依据；本地正文更新不证明其他副本同步，历史观察不证明当前仍存在或一致。仅在当前授权范围同步，未同步的明确其适用身份及影响，不手工改生成物来冒充重建。不按旧命名或静态引用计数判断可删：旧格式兼容、当前共用服务、诊断或动态测试样本分别核实际消费者；分类本身不授权清理，移除／迁移须有对应规格、范围及许可。

在接手时核入口／现行身份，相关修改后核直接引用、版本与取代关系，交付前核当前状态、实际对象与证据能否对账。沿[execution §9](../rules/execution.md#9-检查动作与结论)选择目标项目已有工具或人工核对，写明对象、实际结果和限制；不强制每轮新建检查器、全仓哈希或固定字节前缀。发现缺项、指针不一致或身份无法确认时，报告并暂停依赖判断，独立获准部分继续；结构可解析不证明语义等价或用户确认。

### 文件版本与产品基线

区分产品版本、流程文件自身版本、源码／候选身份、构建制品身份及接口／数据格式版本，不要求编号相同，不做全仓版本串替换；文档修订不自动升产品版本。流程文件在既有阶段稿及变更记录中关联实际内容、修订依据、适用范围和确认状态，具体记录及确认沿 requirements／execution，不另建一套版本台账。真实依赖属于相应源码／构建基线时，引用已有锁定文件或配置定位，不虚构依赖清单或强制采用统一编号规范。

对话讨论与未确认草稿可用可定位的轻量标识；交用户确认、采用、验收、发布或跨项目交接前，固定实际内容及范围，用可回读的提交及路径、不可变快照或内容指纹定位，不能只写日期、“本轮”或“最新版”。编号相同而内容变化是不同对象；旧标识和确认仍属于原对象，新内容须重核受影响引用、证据及确认范围，不把旧指纹换绑到新内容。实际取证唯一沿[checking 的版本取证](checking.md#version-evidence)，不另造算法。

多文件共同构成一个基线时，在既有合同／交付记录中列组成文件、各自固定版本标识、适用范围及来源／确认记录，并关联实际下游消费者；不把不同对象的局部确认合成全基线通过。每次交接核引用的正是该内容，未确认的必要输入明确限制；开发前的上游链及后续承接如下：

| 阶段交接 | 本阶段应固定／引用的对象 |
| --- | --- |
| 启动接续 | 既有需求、设计、实现、运行／发布版本与本次范围；没有同名文件不重启项目 |
| MRD → PRD | 有效目标、首版／非目标、约束和成功依据的指定内容及确认范围 |
| PRD → 架构 | 当前行为、规则、验收及未决项的固定规格；需求改变先按 requirements 处理 |
| 架构 → 模块／组件／UI | 实际相关的系统／数据责任、接口与恢复依据；组件／UI同时引用相关PRD及彼此实际消费的契约，不假定十阶段严格线性 |
| 开发包 | 直接沿既有“实施进入条件”引用固定需求／设计，不另建开发前置表；包内任务不各自暗换上游 |
| 联调／验收／获准交付 | 待测实现或制品、构建／运行条件、有效验收依据及限制；结果能对回实际受测对象 |
| 迭代接续 | 原基线、本次变化、新固定对象及其确认／取代范围，未受影响的有效依据继续沿用 |

上游实质变化按[requirements §3](../rules/requirements.md#3-收全后起草)及[execution §10](../rules/execution.md#10-评审意见返修与成果确认)处理，沿用其纠错、确认和旧证据规则。沿已有“待同步正文”词汇记录受影响落点；实际写入核对后才记“已同步”，必要复核或指定确认尚缺时同时记“待复核”及对应对象，不把两种状态混为一项完成。同步过程中上游再次变化，保留本次实际同步的基线，对新变化重核影响，将相关落点恢复为“待同步正文”或保持受影响复核未完成；无关已完成项不回退，不静默改指针后沿用旧结论。

涉及可运行／可分发制品时，按目标项目已有构建记录保存：来源基线与相关构建条件（平台、配置及适用依赖）、生成时间、制品内容指纹；Git构建注明 buildCommit／buildDirty，非Git来源注明适用身份，不伪填干净状态。脏构建还须定位实际差异的快照或指纹，仅写 dirty=true 无法固定内容；缺身份时保持候选及证据不足。单文件取实际文件指纹，多文件制品明确清单范围、文件数及组合指纹，不默认散列整个开发仓库；不得从旧聊天复制身份。

同一目标、平台、配置及验收用途只保留一个明确的当前验收指针；比较版本、多平台构件及历史对象可并存，但标清身份与用途。替换前核旧对象来源并保留上一有效版本及可恢复依据，直至新对象验证后按许可切换；来源不明残留不覆盖、不复用或顺手删除。涉及数据迁移时先引用[架构的恢复依据](../skills/architecture.md#runtime-delivery)；无法回退的场景须先明确停止、核对和人工处置条件，不承诺失败总能恢复，也不自动回滚用户数据。

新版对已承诺支持的旧接口／数据负责提供有效读取或约定的迁移路径，不支持的对象明确拒绝及后果；改变支持范围先说明实际消费者、数据后果及取舍并取得必要决定，不以拒绝代替兼容承诺，也不默认永久兼容所有旧版。具体机制和组合验证分别沿[架构兼容设计](../skills/architecture.md#compatibility-design)与[组件消费者契约](../skills/component.md#consumer-compatibility)，不在本节另写迁移步骤或因旧名清理兼容层。

验收记录绑定实际受测对象与条件；发布或安装的是另一构件时，先核来源与内容对应关系及必要差异验证，不自动迁移结论。当前源码、验收构件的显示版本可与已发布版本不同，构建内容也可领先；领先、升版或本机刷新不等于发布。动作许可唯一沿 core，交付／安装／部署就位不等于验收；实际交付沿[联调方法](../skills/integration-testing.md#4-用户验收与获准交付)核准许对象、环境和回读。已发布对象不得在同一不可变发布身份下静默换内容；新内容须有可区分身份和适用验证，原报告、批准及发布记录保持原对象。
