# MRD：问题、价值与首版边界

## 是什么、做什么、怎么做

MRD 说明为谁解决什么问题、为什么值得做、首版做到哪里和怎样观察价值。先澄清并持续记录，再收全确认、起草、检查及评审，交给 PRD 细化行为。执行先读 [需求记录](../rules/requirements.md)及 [阶段沟通](../references/stage-methods.md)，不把分析笔记提前包装成正式 MRD。

## 1. 接续、输入与分工

核本次新建／接续／需求变更／只读评审、当前产品、有效目标／约束、需求记录、证据和已有 MRD。用户决定价值、范围、优先取舍、冲突和指定版本；Agent 澄清、分析、记录并提出有依据建议。已有有效确认复用，修改只处理受影响范围。

每次提问或建议前核是否仍在当前产品、来源支持什么、为何现在必要。不能让用户完善示例产品来替实际产品铺路。关键输入不足先说明限制和具体缺口，独立资料整理继续。

**本步落点与继续条件：**在当前需求记录标明本轮对象、来源和已有确认；能确定当前用户问题后进入沟通，不能确定就先澄清。

## 2. 反复沟通、及时暂存

沟通暂存前先读 [需求贯通](../references/traceability.md)，在既有需求记录中关联用户表达、Agent 回述及实际确认到具体问题／价值／范围条目，成文时继续沿此关系核对。

从一个真实用户问题／场景开始，听需求、追问影响理解的缺口、描述可观察效果、回述理解、接受纠正。讨论当前解决办法及不足、用户／利益相关方、约束、首版与非目标、产品类型基线（完整必答六项见第 3 节）、优先理由和成功观察；按当前阶段粒度澄清，不提前问全部接口或页面。

每项经确认立即保存；分批展示现有已确认、新增／变化和待决，而非最后一次汇总。重要取舍与矛盾及时给具体影响、选项和理由，用户决定后回写，依赖分支等待。沟通不设固定轮数，已有确认不重复问。

研究只为当前证据缺口：选择相关用户、实际资料或可靠公开来源，说明样本／时间／局限，区分用户表达、观察事实、建议和假设。需要时比较现有方案；不凭热门产品补功能。涉及模型产品才分析模型必要性和替代办法，使用编程 Agent 本身不构成产品需要模型。

**本步落点与继续条件：**确认事项和变化进入需求记录，证据保留来源；持续核理解与身份，用户未确认暂无新增时继续沟通，不进入正式起草。

## 3. 收全确认后形成正式 MRD

用户明确暂无新增时，基于记录分组展示目标／问题、需求／范围、约束／决定、证据／假设和待决。核遗漏、重复与冲突，取得用户对本阶段当前清单已收全的确认，再写正式 MRD；确认绑定及后续变化统一沿 [需求记录第 3 节](../rules/requirements.md#3-收全后起草)，该确认与文档通过分开。重要核心矛盾未解决不依赖它成文。

正式正文说明使用者、任务与问题证据、价值目标、首版／非目标及取舍、约束／假设、成功观察与来源（需要单页组织提示时见 [MRD 单页组织提示](../assets/templates/mrd.md)，已有载体可沿用）；并记录现有解决方式／替代方案（采购、复用、流程改造、不做）及选择理由、利益相关方与决定权（对话者、目标用户、有权决定者、验收者、发布批准人、平台／部署操作人；无法确认标未知）。

正式 MRD 必须写明产品类型基线（本清单是唯一定义，其他文件只引用）：

| 类别 | 内容 |
| --- | --- |
| 必答六项 | 形态与载体、平台与生态、端与运行环境、用户与租户、部署与交付、交互入口 |
| 条件项（按实际适用） | 模型/Agent 行为、数据与合规、规模与性能、外部集成与硬件、发布与分发、国际化/无障碍、现有技术栈与组织约束；可按未知或不适用＋依据裁剪，不强制无关项 |
| 必答三态 | 明确；用户确认“暂不决定”并记录影响与解除条件；缺失且未说明 |
| 含模型/Agent | 写明自建或框架；框架名称／版本可候选待定，但须交架构比较核查（内容与官方文档、可复用能力／限制／缺口／证据、复用边界），不得以“待定”跳过或假定能力 |
| 完成判据 | 必答项“缺失且未说明”不得记 MRD 完整；“暂不决定”可完成，但只阻断依赖该基线的 PRD／架构设计，并随交接带影响与解除条件 |

平台有官方规则时（如应用商店、小程序、鸿蒙、苹果等），基线还须记录已知平台官方规则约束（审核／上架、隐私／权限、技术／设计限制、分发／资质）与未知项；影响首版范围或可行性时交用户决定，缺失按未知／不适用标依据。

**示例（模拟，不是当前项目需求）：** 企业内部知识问答助手。产品类型基线：形态与载体＝agent／Web 应用；平台与生态＝Web 浏览器＋公司云；端与运行环境＝桌面与移动浏览器、在线；用户与租户＝内部员工、单组织单租户；部署与交付＝公司私有云部署（单租户）；交互入口＝对话式＋Web 界面。条件项按实际：模型/Agent 行为＝使用内部 Agent 框架 A（版本候选待架构核查）；数据与合规＝公司内部资料；规模与性能＝约 500 人；外部集成与硬件＝文档库、SSO；发布与分发＝内部灰度；国际化/无障碍、现有技术栈按实际说明。示例只说明填法，不新增产品事实或默认业务。

具体 MRD 条目承接对应确认记录，拆分、合并或取舍说明依据，并核专业转写与已确认含义等义。指标只用有效依据；没有基线、数值或效果证据就标未知和验证安排，不编默认阈值。价值验证说明对象、方法、责任、时点与必要成本；依赖产品内数据时，把观察所需数据／事件／分组／基线采集条件列入给 PRD 的输入；详细运行交后续设计。

**本步落点与继续条件：**正式 MRD 沿项目既有位置形成草稿，收全依据保留于记录；核稿件确由该清单展开后进入逐项评审。

## 4. 检查与评审

按记录逐项核实际正文落点，并从各 MRD 条目反查具体来源及拆合／取舍依据，核是否正确保留目标、范围、身份与确认；检查问题→用户任务→价值／成功依据是否连贯、是否擅增或漏掉已确认要求；核 §3 产品类型基线的必答项是否按三态记录；含模型/Agent 行为时自建或框架及候选边界是否清楚。随后核受影响链接／结构，结论按 [实际检查顺序](../rules/execution.md#9-检查动作与结论)形成，不能用文件存在判合格。

缺陷按根因规则修直接关联；上游理解改变回到相关沟通／确认，不为了消除矛盾静默删要求。只读评审交意见及影响，不代改稿或签通过。收尾说明对象状态时只写来源支持的事实：来源未提供的状态记未知，不写成“未形成／未就绪”；只说明本轮动作时用“本轮未制作／未执行”，不据此推断对象不存在或历史未形成。

## 5. 完成、停止与 PRD 交接

交指定 MRD／版本、覆盖核对、实际检查、未决／待验证与影响，用户决定阶段结果。获准后向 [PRD](prd.md)交具体条目及其来源／确认关系、有效任务、价值、范围／非目标、产品类型基线（含框架候选／核查请求）、成功依据、约束和需求记录；未知保持身份。未获下一阶段许可则停止，恢复先读现行版本和变更，只补失效范围。

本阶段交接包按[阶段交接物格式](../references/stage-methods.md#阶段交接物格式)组织：需求记录与确认、问题／价值／范围条目、指定 MRD 与产品类型基线、成功依据、下一层 PRD 及路径引用；产品类型基线按 §3 的完成判据核对：缺失且未说明不得完成 MRD 或交架构；暂不决定项随交接带影响范围与解除条件；框架候选待定交架构核查。其余通用字段、五类状态与模板沿格式节。

**成果最小清单（完成前核对）：** ①问题、受影响用户与现有方式缺口；②价值与首版范围／非目标；③产品类型基线六项（含暂不决定／未知依据）；④替代方案与选择理由；⑤可测成功标准（指标＋基线或未知＋观察安排）；⑥平台约束、风险与假设；⑦来源与确认。缺①—③标缺口，不默认记 MRD 完整。
