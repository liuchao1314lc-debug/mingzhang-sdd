# 开发：逐功能实现与局部验证

## 是什么、做什么、怎么做

开发把有效规格／设计转成真实实现和局部证据。支持基础准备、功能／根因修复、仅计划及只读评审。按当前功能合同→计划／任务→实现→局部验证→符合性／质量评审→交接推进，不一次实现所有未来功能。共用动作见 [阶段组织](../references/stage-methods.md)。

## 1. 核输入与实际环境

核当前功能、有效需求／验收、相关架构／模块／组件／UI、产品类型基线与已核框架范围、现有源码／运行方式、工作区和许可；保留无关改动。Agent 实现目标项目获准功能、运行获准检查并报告，用户决定新范围、重要取舍和指定成果。技能本身不提供执行工具；读取、编辑、搜索及检查从 Agent 已注册工具列表中选择，缺少时向用户说明缺口（沿[工具使用与检查](../references/checking.md)），不为执行本技能自制工具。目标项目的业务代码与已获准功能测试按其有效规格落实。

基础准备先复用现有最小启动、测试和配置，只补当前实现缺口，不默认安装框架、CI、服务或新治理体系。运行、付费、私有资料外发、安装、Git 与发布核各自当前许可；不得把“启动开发”扩为所有外部动作。

上游尚未确认时，只在获准起草／探索范围形成注明身份的草稿；草稿或技能资源制作批准不等于目标功能通过。仅计划模式不实现、不运行测试。干净检出复现须在获准隔离位置进行，不清空当前工作区；未做时不能以本机可跑冒充干净环境可复现。

**本步落点与继续条件：**环境、工作区基准、有效输入与许可进入当前任务记录；能界定当前实现对象后计划，只有计划许可不写源码。

## 2. 明确一个功能合同和顺序

首次展开包内任务前，先读 [需求贯通方法](../references/traceability.md)，沿已有唯一关系入口落实任务来源及下游结果。

先对当前获准范围形成开发包清单与开发路线，再展开包内任务。开发包是通用工作包在开发阶段的具体形式：围绕一个可判断的交付目标，组织必要实现、测试和说明；可以跨模块／前后端，不等于文件、目录、角色或提交。包内小任务共同形成同一结果时合包；目标可分别交付、依赖不同或长期无法形成反馈时拆包。不设固定文件数、天数或任务数，小改可只有一个包并合并载体，不规划全部未来功能。

每包沿已有合同／计划明确标识、需求依据、目标、范围／非目标、输入输出及异常、前置／接口契约、交付内容、执行者与修改边界、实施进入条件、验证和完成条件；复用模型/Agent 框架前核对当前版本与架构已核能力范围；超出即停止依赖该能力的包／任务，回架构补核并更新架构正文，不重复实现已有能力；开发包只记录复用／自研／延后决定及引用版本，不另造能力清单。**示例（模拟，不是当前项目需求）：** 当前框架 A 已核范围＝对话循环、工具调用、流式输出（版本 v1.x，核查证据在架构记录）。本开发包只用这三项；审计日志按架构缺口自建；“多工具并行”未核，不假设可用，列入延期；在包记录中写清复用／自研／延后理由。示例只说明复用前核对的写法，不新增能力或开发任务。

按架构固定的平台规则约束实施：权限／隐私声明、签名／账号、审核材料等按约束落实；未核项不假设，交联调时列出平台待办。

建包时在既有合同形成或刷新“实施进入条件”：引用上游交接中的有效需求／设计标识与版本、异常／权限后果、执行者与失败负责人、可观察验证入口、未决项与解除条件；上游只交可引用条目，开发不在上游正文外另造合同。

展示重要假设和取舍，沿用有效确认；新的重要决定取得后才实施。路线明确真实依赖及原因、启动条件、可并行组、必要串行环节、包间汇合检查和交接，不只列先后编号；近期包细化到可执行，后续包保留必要轮廓，变化后更新受影响关系。

执行者来自实际指定或获准使用的人员、当前 Agent 或获准协作 Agent；协调者维护路线、分工与汇合。评价方不能参与被评价实现及开发者自检编写。并行须同时满足成果依赖已解除或可由明确契约／替身隔离、修改边界可协调、共享状态／环境无冲突、实际能力和许可具备；共用仓库不自动要求串行，不同文件也不自动独立。接口已定可先用替身并行实现，真实集成仍等待必要上游；语义未定或无法隔离的冲突环节串行，只停受影响分支。宿主无并行能力时按路线串行交错推进，分别登记“规划可并行／实际并行／串行交错”，不得将交错记成并行。并行规划本身不产生新增 Agent、外部调用或环境操作的权限。

包内小步实现、评审和验证不必等全包完成；每个节点对应能单独判断结果的增量，只登记该增量已检查及对象版本，不折算开发包验收数。包内评审是开发者自检，不产生独立评价身份或新增用户裁定节点。评审与用户裁定以开发包批次或完整候选版本为单位开轮，同一轮内多项成果与多条意见合并一次回执、逐条理由保留但不逐条开轮，只有包边界变化、重要取舍未定或必要缺口未消除才另开一轮。成批不减免共用返修的逐条取舍及复查；必要裁决和偏差仍按共用执行规则及时呈现，不等批次结束，也不新增每步审批。

包间汇合检查核接口、数据、调用和相关失败衔接，只形成指定对象的局部证据，不签系统任务通过或用户验收，不自动启动联调。包完成须实际交付及必要检查成立，不能只数任务勾选；开发包完成数、独立评价工作包数及行为覆盖数分开。两者不是完成数一对一：一个评价工作包可覆盖一个或多个开发包，须按任务固定映射，不默认拆包或合包评价。明确安排独立评价时，固定其所含开发包标识、版本和行为范围，不以局部重测替整包覆盖。范围／契约变化后核受影响包及旧证据，阻塞登记原因与解除条件，独立包继续；按包交实现、证据和未验证项，获准后再交联调。

制定测试方案须结合当前项目的实际需求、风险、技术条件和时间／成本约束，参考与测试对象相关的 [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)、[Google](https://testing.googleblog.com/2024/10/smurf-beyond-test-pyramid.html) 等官方成熟最佳实践建议，注明参考来源与适用理由，按项目实际选择方法、范围和用例；不照搬固定用例数、测试比例或工具流程，不以外部建议替代已确认需求与验收标准。

含模型行为的功能，计划时先按[第4节模型评测方法](#model-evaluation)确定需要的输入、预期、对象身份和执行条件；样例可以逐步落实，不能执行后才按实际输出补写预期。

任务按依赖排列，每项说明实际承接的具体需求／验收子集、设计落点、承接理由，以及对象、动作、结果与实际检查。任务可继承包的固定基线，但不能只挂整包标识、整份 PRD 或笼统目标；沿关系应能反查具体 MRD／经确认等效条目及有效决定。共用技术／测试任务保留多来源，分别说明支撑要求及必要性；来源不明先澄清，不硬挂编号。新建／修改／删除／重命名均核对应基准，不把全部脏文件排除导致漏掉本次改动。任务完成不能只看文件存在或编号打勾。

规划位置与实际入口沿 [成果登记](../references/stage-methods.md#成果入口与验证载体)区分；CODEMAP／等效地图只登记核实的实现，不为计划生成另一张实际职责地图。“实现—任务—证据表”引用同一关系中的具体节点，是另一视图，不重复维护需求—模块／组件映射。

**本步落点与继续条件：**开发包清单、路线及包内合同／计划／任务沿既有功能位置保存；包边界、依赖和验收明确、必要决定及许可具备后，按路线启动已就绪包。

## 3. 小范围实现与根因修复

根因修复开始前先保存可复现的失败证据：预期／实际、命令、输入、环境与原始输出；无法复现时记录限制与已有证据。修复后用同一复现及受影响调用方复核，不把“写了一个通过的测试”当回归成立。

按最小可检查增量实现本功能，随关键偏差报告具体事实和影响。问题按 [根因规则](../rules/execution.md#8-根因与修复)处理；先定位原因和最小完整影响范围，再选解决方案，不叠补丁／改标准凑绿。保留有效测试、用户工作及历史证据，不顺手重构无关区域。

实现中发现需求冲突，先指出有效规格与实际代码的差异，反馈受影响的需求／设计并取得必要决定，不以代码反批规格。复用框架能力前核架构已核范围；超出先停包回架构补核并更新正文，不重复实现已有能力，不在开发侧另造清单。试验成果进入正式实现须有采用依据与当前许可；试验成功、空实现、模拟返回或成功标签不能记为正式功能完成。

将任务关联到实际形成的代码、配置或技能正文及其内容身份，核实现怎样落实所承接的具体要求；计划位置保留规划状态，不用任务完成标签代替实际产出。

**本步落点与继续条件：**实际实现写在允许对象，任务记真实进度；重读写入结果并核改动范围后进入局部验证，未形成项保持未完成。

## 4. 实际局部验证和评审

依据改动运行必要测试／检查，先取得原始结果再核是否命中目标分支，按 [检查顺序](../rules/execution.md#9-检查动作与结论)下结论。有意义的缺陷回归应能识别修复前错误，修复后成立；纯低影响文字改动用内容／关系核对，不写镜像实现的测试。

先核规格符合性，再按改动面选择相关维护／质量风险；只核实际触及或直接影响的要求，未涉及领域不逐项展开或写“不适用”流水账，已知真实风险不得省略，适用项引用架构系统验证策略。仅在当前要求之外、为尚未证实的风险新增防护、检查、抽象、重试、替身或平台工具时，说明具体失败路径、影响、现有覆盖与成本；普通必要实现和验证沿已有依据继续，不逐项例行报告，重要新增取舍交用户，不自行扩大改动范围。输入有效性在进入当前信任边界时对同一值校验一次；同一输入、适用规则及信任边界保证未变且已验证时不重复校验。输入、适用规则或信任边界保证变化时，重验受影响的输入有效性条件；授权、业务状态和副作用按当前操作要求独立核对，不因输入校验通过而省略。实现风格服从仓库既有约定和实际可读性：函数抽取、正常流程与校验细节、注释密度按该约定处理；本技能不另设单次使用、分支数量或注释比例门槛。对由明确生成源及既有生成流程维护的文件，按既有流程改源重建，具体沿[项目资料与版本治理](../references/project-governance.md)。测试优先真实实现，不把业务逻辑复制成测试预期；替身按第2节边界使用，保留内部已定接口的并行替身。沿用仓库现有工具与流程。失败保留原结果并定位修复，重核受影响项；必要检查通过后，除新变动／失败／疑虑外不机械反复全量运行。替身与真实依赖、静态内容与模型效果分开。

分别关联具体需求／验收、任务、实际实现、用例与原始证据：用例指明核什么要求及预期，执行结果绑定真正受测的实现版本／条件：基础提交＋未提交范围清单（实际文件）＋内容指纹或获准快照，不只用 HEAD、日期或“本轮”。未执行用例不登记为实际证据，证据只支持已覆盖的子集；关系齐全仍须核实际行为与原目标是否一致。

<a id="model-evaluation"></a>

产品确有模型行为时，Agent 将有效验证策略落实为可复核的评测材料与结果，按以下顺序做；普通软件不因使用编程 Agent 而自动增加模型评测：

1. 从已确认要求选本功能必要的正常、相关失败与禁止情形，先写每个样例的输入／前置、允许动作、预期结果及判断依据。预期来自有效规格，不从待测输出或厂商默认评分反推；重要行为歧义先交用户决定。
2. 在既有计划／证据位置固定实际模型、提示、工具／配置、相关数据及样例的版本或可恢复副本身份，关联具体预期。两版比较使用共同请求、条件和判据，注明真正改变的对象；不强制评测平台或每项重新做哈希。核当前调用／资料许可、时间／费用上限及可取得的回执；执行前固定重复次数、预算与容差，不足则只准备材料。
3. 获准后执行，保存逐样例真实输出、相关工具调用／返回、执行状态及对象身份；替身与真实分开。超时或未知结果先核原动作，未取得证据不填成功，不用退出码或代码测试替代模型任务判断。
4. 模型／随机行为的统计性结论不得凭单次通过或失败，但一次即可确认明确违反有效要求（越权、数据破坏、禁止情形等）的结果，直接按违规／缺陷报告，不以统计波动掩盖。对照预先固定的结果与禁止情形逐项判断，记录满足、偏差或证据不足及理由，明确样本／条件限制。结果或预算未明不签整体通过；改变模型、提示、工具或样例后按实际影响复查，不把少量通过扩成未测行为或长期收益。

原始结果和分项判断沿既有证据位置交接，用户按指定成果确认；明确安排独立评价时再沿下述独立规则，不由本方法自动增加评价方或模型调用。

明确安排独立测试时，评价方按 [独立测试规则](../rules/independent-testing.md)从固定要求自行设计（触发与交接索引见该规则开头）；Agent 开发者的局部测试仍是自检。交评价方有效要求／禁止情形、被测版本、运行条件及许可，自己的测试结果只标补充；获准整改后按因果影响交独立重测，不默认让本实现者代签独立评价。

**本步落点与继续条件：**原始结果与分项采用进入既有证据位置，符合性／质量意见引用实际对象；必要缺口先修正再复查，核验完成后交付。

## 5. 交付、停止与联调交接

交实际实现位置／版本、本功能变化、每任务具体来源及实现／用例／证据关系、局部结果及原始证据、未完成／未验证、运行方式及必要风险；使用框架时另交框架版本、已核范围与复用／自研选择依据；不能把局部通过写成系统／用户验收。用户按实际范围确认成果，提交不默认发生。

获准后向 [联调测试](integration-testing.md)交确定实现／环境、系统任务与验收、依赖／替身限制、缺陷和有效局部证据。无联调许可停止。恢复核工作区／版本、任务和未知动作状态，先核原结果，不盲目重跑副作用。

交接给联调的交接包按[阶段交接物格式](../references/stage-methods.md#阶段交接物格式)组织：实施进入条件与固定输入、任务来源子集、实现版本、局部证据、异常与未验证、框架复用依据与已核范围（如适用）、联调输入及路径引用。其余通用字段、五类状态与模板沿格式节。

**成果最小清单（完成前核对）：** ①开发包／任务与需求来源；②实施进入条件；③实际改动与受测版本；④局部验证／缺陷复现证据；⑤适用质量风险、检查结果及必要排除说明（沿第4节）；⑥未完成／未验证与运行方式；⑦联调交接。缺②③④标缺口，不默认记包完成。
