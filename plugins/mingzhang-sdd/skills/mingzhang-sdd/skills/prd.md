# PRD 成果方法

## 是什么、做什么、怎么做

PRD 把已确认的用户问题、目标和范围转成产品行为及验收，位于 MRD 之后、架构之前。交付能说明用户如何完成核心任务、异常后会发生什么、怎样判断结果的具体规格，支持起草、修订及只读评审。

按以下步骤核有效输入、展开行为、处理必要歧义、形成正文、自检、完整产物独立评价和交付。作者 Agent 形成成果并做内容自检，独立评价方按第 5.1 节评价完整产物，用户决定重要取舍与指定版本；模板、工具和本技能不代用户批准。执行前先完整读入口指定的共用规则、[需求记录](../rules/requirements.md)及[阶段沟通](../references/stage-methods.md)，通用操作不在此重写。

## 1. 接续与有效输入

核当前请求、目标项目／对象／版本、用户任务、允许动作，以及有效 MRD 或等效价值／范围依据、已确认产品类型基线（平台／端／入口及已知平台规则约束与未知）、现有 PRD／需求／验收和实际决定。沿用既有确认；缺同名文档不重启 MRD。依据不足明确限制受影响判断；获准整理可把未知保留为假设／待决，不能写成已确认产品要求；正式起草还须满足需求记录的收全前置。

只读评审不写 PRD；修订只动相关正文及必要关联，保留编号、历史有效确认和无关工作。发现目标／价值改变先显化 MRD 影响；技术选型、模块分配和界面呈现留给后续设计，不在此借细化扩业务。

接续当前任务时，先确定本次要判断的对象、改动及实际验证，覆盖只读完成核对；所需修改前来源在首次相关写入前准备，条件和成果版本在动手前取得，不能等改完才补基准；没有本次动作的只读任务不制造写入链。需要工具时沿[工具使用与检查](../references/checking.md)选择。

**本步落点与继续条件：**核对结果进入本轮记录，确认价值／范围足以支持当前任务后展开行为；缺口只限制对应任务。

## 2. 从用户任务展开具体行为

先定位具体 MRD／经确认的等效条目和实际用户结果，再写角色、触发／前置、输入、用户操作、产品响应、结果。核心任务必须真正展开，不能只写能力名单、页面、需求编号或指向另一方法。按可判断的决策批次向用户展示操作、响应与结果：高风险、价值、权限和异常后果单列，低风险同义项可合批并记录沿用依据；关键理解确认后立即暂存；矛盾说明具体影响并由用户决定，变更保留原／新内容和确认。正常路径形成后，补相关空数据、权限不足、失败／取消／超时、重复与恢复的触发、可见结果、状态／数据影响及用户能做什么。

已有正式版本的产品，还须覆盖存量数据、进行中流程、旧版本客户端、灰度／分批与回滚后的用户可见状态；技术迁移机制留架构，产品只定用户看到什么、能做什么。

关键术语首次出现时给定义，后续用同一正式术语；用户口语别名可保留但不作为正式名称；术语变更按需求变更核受影响行为、验收、追踪与下游正文。

记录或引用完整角色映射（对话者、目标用户、有权决定者、验收者、发布批准人、平台／部署操作人）；有效决定来自有权决定者，对话者确认不代替预算／合规／验收／发布批准人的确认，未确定者保持未知。

每项功能及适用非功能沿用稳定标识、记录来源、作用范围、优先级／理由、版本／确认状态及前置需求；优先级使用 MRD 或项目约定定义的最小语义（如阻断上线／首版必需／可延后），每项说明归属与理由，新增高优先项回 MRD 核对首版范围；示例不是默认业务。无来源建议保持拟议或删除。重要语义缺口按影响和不确定性就地标记，按共用规则的 PRD 材料范围整理；真实决定回写对应行为、异常与验收，不只留问答记录。独立可开展部分继续。

**本步落点与继续条件：**行为／异常理解在需求记录按任务暂存，核用户真实反馈和冲突后再细化验收；未收全不形成正式稿。

## 3. 验收与追踪

维护本节需求关系前先读 [需求贯通](../references/traceability.md)。

每项本版需求对应可判断的前置—事件—预期结果，指明观察对象、方法和证据；必要异常／权限分支不能只给成功条件。功能验收与长期价值观察分开，数量／指标从目标项目有效依据取得，不填通用默认阈值。目标或价值依据含易用性时，由用户确认可观察的体验判据（无需外部帮助完成、错误可恢复、关键状态可理解等）；无依据标未定，不引入默认值。业务对象、关系、术语及生命周期只补影响理解和验收的内容，不先设计数据库。涉及权限时形成角色—动作—对象—范围—拒绝后果矩阵；涉及多状态／数据对象时形成关键实体、状态转换、错误／空／加载／未知矩阵；涉及非功能时按适用写指标、条件、测量与依据，无依据标待定，不填默认阈值。只列会影响本版行为或验收的角色、状态和非功能项；同义分支合并；不涉及不建空矩阵，不穷举不影响判断的状态。

产品含模型行为时，按本项目实际任务定义允许资料／工具动作、确认／拒绝／撤回、结果核实、退出／接管、预算和不可信输入等相关行为及验收；真实模型／外部动作另核许可，不因定义评测而运行。已有真实失败按来源引用，没有就保持缺口。

沿需求贯通方法，在项目既有唯一追踪位置关联具体 MRD／经确认的等效条目及有效决定、PRD 行为／异常、验收和计划验证，说明每项细化实际承接的目标／范围及理由。核首版任务是否漏项，从各行为／验收反查具体来源，核前置是否本版有效、异常及术语是否一致；模块、组件、实现和证据到实际形成时再登记，不维护第二份完整需求。

**本步落点与继续条件：**把需求对应的验收、来源关系和必要假设记在当前分析／需求记录，核条件可观察及来源有效后准备收全展示。

## 4. 形成实际 PRD

先基于持续记录展示本阶段需求及行为／异常／验收，取得用户明确收全确认并解决影响起草的冲突后，再起草正式 PRD。已有文档变更只核受影响范围并沿用有效确认；确认绑定及后续变化统一沿 [需求记录第 3 节](../rules/requirements.md#3-收全后起草)，纯文字纠错和只读评审不重做收集。采用现有规格结构，必要时参考 [组织提示](../assets/templates/prd.md)。有写入许可才在目标项目写入并核后状态；候选、获准写入、实际写入和用户确认分别记录。新增内容能对应已确认目标及当前必要性，不能因模板有字段补业务。

在业务核心行为、异常结果、权限或验收尚未决定时，受影响部分保持待决；待验证假设要有对应需求、条件、验证阶段／责任和不符时处理。接受风险不能代替需求定义或动作许可。

**本步落点与继续条件：**正式 PRD 草稿写在项目已有规格位置，收全确认及记录关联可定位；所需改动取证依第 1 节在修改前准备，实际写入后保留动作及收尾原件，再做检查，不把候选当实际文件。

## 5. 检查、采用与内容自检

先做产品内容自检：核心任务展开、异常结果、验收可判断、来源与追踪、拟议与确认分开；再按第 1 节所选必要项实际调用 Agent 已注册工具并保留可回读原始返回，核对象／版本／条件与适用范围。文件存在、工具成功或人工摘要不替代内容完整；未执行、证据不足和业务不满足分别保留。工具选择、检查顺序与缺失处理沿[工具使用与检查](../references/checking.md)和[执行第 9 节](../rules/execution.md#9-检查动作与结论)；只读 PRD 任务执行适用检查，但不写稿。

本方法只补 PRD 语义承接、目标／范围漂移和基线冲突：对照具体 MRD／等效条目及有效决定，核第 2／3 节及确认记录的承接正文、细化含义与未纳入理由；文件存在却只有能力名单、异常后结果未定义，按核心未完成处理；冲突回 MRD 或标受影响范围，不带着已知冲突进入阶段确认。确定缺口交回对应正文修正，事实／接口不足只限制依赖判断，失败保留原始状态。

### 5.1 完整产物独立评价

完整稿形成并完成作者自检后、交用户确认阶段版本前，按[PRD 专用独立评价](../rules/independent-testing-prd.md)提交指定版本完整产物与固定依据；评价状态（通过／失败／未执行／未安排）随交付记录。未执行须用户明确接受风险、影响与交接，并给最小评价范围，不宣称整稿独立通过。完整范围、评价方独立性、原件保全、判定与整改重测沿该文件；不另维护流程，也不由作者自检代签。

## 6. 交付、确认与交接

按共用规则直接发送真实成果／版本、变化、作者自检、完整产物独立评价的覆盖／实际结论或未执行状态、未完成／未验证与影响、必要决定和接续输入；消息表达见 [用户提示](../references/messages.md)。缺口或部分失败也交已有成果，独立评价不能被自检替代。用户实际确认绑定指定版本，单独确认 PRD 不自动启动架构；若同一回复另授权下一步，分别登记范围。

可向后续架构交有效规格／确认依据、具体来源与本版需求／验收的对应、数据／权限／非功能／外部依赖行为及待验证风险；获准后按 [架构方法](architecture.md)接续，未获许可则停止。恢复核现行 PRD、变更及失效证据，不重问有效确认。当前结果在目标项目已有记录或交付中保存，不新建工作流服务。

交接给架构的交接包按[阶段交接物格式](../references/stage-methods.md#阶段交接物格式)组织：MRD 条目与产品类型基线、PRD 行为／验收、指定 PRD 版本、架构输入及路径引用；业务异常在 PRD 明确，技术细节留设计。其余通用字段、五类状态与模板沿格式节。

## 7. 详细产品规则的开发前边界

当前任务的详细产品规则唯一落在本 PRD：角色与触发、正常／相关异常结果、权限与数据后果、状态变化和验收依据须能判断；仅有能力标题不具备交设计条件。重要业务取舍由用户决定，Agent 负责提出完整选项、落正文并核一致，不能将实现便利改成产品标准。跨层冲突先回对应责任层，受影响设计等待，独立部分继续。

交架构时标明本版已明确范围、固定对象、待验证假设及未定项影响；组件／UI 和开发包合同引用这些规则，不另写第二份业务标准。未来功能细节可后续细化，当前包关键行为未定不得进入依赖实现。阶段规则的完整性自检与用户指定版本确认分开，沿 [实施进入条件](../references/stage-methods.md#实施进入条件)交接。

**成果最小清单（完成前核对）：** ①核心任务端到端行为与结果；②异常／权限／数据／状态分支；③可判断验收及来源；④角色－权限映射；⑤适用非功能与体验判据；⑥需求—验收—追踪；⑦待决／拟议与确认分开。缺①—③标缺口，不默认记 PRD 完整。
