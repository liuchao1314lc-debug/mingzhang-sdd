# 架构：系统链路与技术取舍

## 是什么、做什么、怎么做

架构把有效产品行为转为系统结构、运行链路、技术决定与系统验证安排。按输入核对→主链路→重要路线选择→职责／接口→风险验证→评审交接执行；不提前实现产品。共用动作和沟通见 [阶段组织](../references/stage-methods.md)。

## 1. 输入、模式与分工

新建设计、已有设计接续／修订或只读评审均核有效 PRD／验收及确认、产品类型基线（含模型/Agent 自建或框架候选；暂不决定项只限制依赖该基线的设计）、现有系统、技术环境和约束。用户决定影响产品／成本／许可的重要路线及指定版本，Agent 分析可行性、设计、核验并报告。缺有效行为只限制对应设计，不用技术方案代替业务决定。

**本步落点与继续条件：**在架构任务记录定位输入／版本及限制；受影响需求已明确后设计对应链路。

## 2. 先说明端到端方案

选择当前核心任务，画清输入、处理、资料／状态、工具／外部边界和可见结果，并走正常及重要失败路径。区分宿主动作、程序判断、模型建议与真实返回；每条边说明谁发起、谁负责、返回和汇合，不能用概念名单代替链路。

在据此细化前向用户展示主流程和关键分支。

使用模型/Agent 框架时，在细化结构前先核查框架内容与官方文档或内部框架的官方来源（内部文档、仓库／接口文档或维护者书面确认；记录来源类型、版本／日期；均不可得标未核，不假设能力；覆盖本产品所需能力），形成可复用能力清单、限制／许可、缺口与不重复开发结论并保留证据；框架候选待定时先比较并记录选定依据；未核查不得假设能力或重复自研。核查结果与复用边界写入架构正文，模块／组件只引用。**示例（模拟，不是当前项目需求）：** 上述知识助手拟用内部 Agent 框架 A（版本 v1.x）。核查记录：可复用能力＝对话循环、工具调用、流式输出；限制＝无租户隔离、单轮工具预算需自设；许可＝内部许可允许私有部署；缺口＝审计日志与权限过滤需自建；候选比较见架构记录；结论＝复用已核能力、不重复自研，审计与权限列为系统自有责任；交接模块时附该清单与复用边界。示例只说明核查和交接的写法，不新增框架能力事实。

产品平台属于有官方规则的市场（应用商店、小程序、鸿蒙、苹果等），或规格明确涉及该平台时，在路线与结构设计前核查本次实际平台的官方规则（审核／上架、隐私／权限、技术／设计限制、分发／资质），记录官方来源、版本／日期、适用条款、平台约束与待办、冲突／缺口及对路线／验收／交付计划的影响；官方依据不可得时记录未知、受影响范围与依赖限制，不凭记忆或第三方摘要宣称合规；交接模块时带约束与待办，发布前按届时有效规则复核。平台核查记录、平台约束与待办唯一在架构正文维护；MRD 只保留已知约束与未知，不复制详细条款；模块／组件／开发只引用，不另造平台清单。

重要技术取舍比较有实质差异的可行选项，按有效质量需求、复用条件、环境、维护、成本和风险说明理由；已有决定沿用，不强制凑选项数量。必要的当前技术事实核可靠原始来源；没有依据标待核，不凭经验宣告可用。

**本步落点与继续条件：**把链路和决定理由写入架构分析／草稿，用户重要路线选择进入既有决定记录；核链路有输入、处理和可见结果且必要决定已取得后细化。

## 3. 细化结构、数据和契约

<a id="compatibility-design"></a>

关联系统责任前先读 [需求贯通](../references/traceability.md)。选定方向后明确系统职责、数据／状态权威、主要依赖、读写与调用边界、输入输出、异常／未知和权限。对权限、数据访问、重复提交等关键约束，走查写清“何时→谁／哪个接口→按什么条件判断→失败／超时的可见后果”；可用已有接口重取或过滤时写明，不发明上游未承诺的接口。

将共享约定放唯一位置；沿该方法在既有关系中标出具体 PRD／验收子集、承担机制及理由，共享机制各来源分别说明承接范围，不复制行为全文。变化影响已有调用者、保存数据或历史证据时，记录实际消费者、原承诺、支持与不支持的新旧组合、迁移或拒绝后果、负责人及停止／回退条件；未改变则不编迁移方案。

按当前任务和有效质量要求选做适用设计并引用已有正文：安全（信任边界、认证授权、敏感数据与失败）、数据（分类、所有权、保留／删除、迁移）、部署（环境、配置、升级／回滚）、可观测性（日志、指标、告警、责任人）；不适用项说明依据，不涉及不生成空表或专项章节，不新增专项方法或固定模板。只设计支持当前任务及必要质量要求的机制。模型／付费／外部服务确实存在时，说明可信输入、工具许可、预算与用量未知、取消／释放和人工接管；未知副作用不自动重试。

**本步落点与继续条件：**在架构唯一正文维护责任、数据与接口依据；核状态权威和调用／异常责任不冲突后安排风险验证。

## 4. 关键风险与系统验证安排

识别会推翻路线的技术假设，说明最小调查／试验、预期观察、许可／数据／成本及停止条件。设计走查可在当前许可内做，真实采集、调用、安装或写入环境另核已有许可；未执行试验只记计划。

试验代码与结果不构成正式产品功能；依据真实结果说明保留、调整或延期，进入正式实现须有采用依据与当前许可，开发沿其对应步骤承接。

系统级验证说明各层覆盖什么及证据关系，局部检查、替身、真实端到端和用户验收分开；依据现有策略维护，不能在各层另造评分体系。相关可靠性／性能／恢复场景要有有效标准来源，不随意定次数与上限。

<a id="runtime-delivery"></a>

交付涉及运行、部署、升级或数据迁移时，Agent 在本节形成可交给开发／联调的运行与恢复依据，按以下顺序做：

1. 从有效 PRD、现行系统和目标环境选出本次实际涉及的场景，核必要环境／配置、启动或变更入口及执行者；引用已有运行说明，只补缺失部分。不涉及的场景说明依据，不生成整套运维方案。
2. 对各适用场景串起“前置条件→执行动作→可观察正常结果→失败停止／恢复”。正常与停止判据引用有效要求；写清谁观察、谁处理、恢复需要什么条件、对已有数据有什么影响。无法恢复或后状态未知时，明确限制、核对入口及需用户决定的处置，不预设总能回滚。
3. 按实际风险走查相关正常／失败／恢复分支，核执行者能否从输入找到动作和结果、受影响数据及处理责任能否交接。重要环境、费用、数据后果或恢复取舍先展示给用户并取得必要决定；机制未定先补设计，未获真实操作许可只做设计走查。

依据唯一维护在架构既有正文，模块／组件细化所需责任与契约，联调引用并核实际条件；设计走查不计真实运行成功。必要机制与未决影响明确后，才交受影响的开发／联调任务。

**本步落点与继续条件：**风险、试验计划／真实结果及系统覆盖进入架构既有位置，原始试验结果另引用；分清未执行与已执行后才评审。

## 5. 检查、完成与交接

实际核具体需求→链路／机制→验证安排覆盖，并从各机制反查来源子集与设计理由，核其承接含义；适用的[运行／恢复依据](#runtime-delivery)能支持对应动作与结果判断，重要失败有负责人，状态权威与依赖一致，决定有依据和真实确认；使用模型/Agent 框架时核 A-31（框架核查结果与复用边界）；平台有官方规则时核 A-32（平台核查记录、约束与待办覆盖）；依 [检查顺序](../rules/execution.md#9-检查动作与结论)形成结论。根因修正限相关设计，改变需求回 PRD，不回改已通过上游来迁就方案。

交指定架构、实际走查／试验事实、风险和接续前置，用户确认该版。获准后向 [模块](module.md)交职责边界、数据权威、接口依据、系统验证策略及适用运行／恢复依据；使用框架时另交框架核查结果、复用边界与已核版本范围；平台有官方规则时另交平台核查记录、约束与待办。设计版本确认不等于组件／真实调用许可；未获后续许可停止。恢复核版本、决定、假设和失效证据。

交接给模块的交接包按[阶段交接物格式](../references/stage-methods.md#阶段交接物格式)组织：PRD 与产品类型基线、需求子集与机制、架构版本、框架核查结果与复用边界（如适用）、平台核查记录与约束／待办（如适用）、验证与风险、适用运行／恢复依据（如涉及）、模块输入及路径引用；未核查的框架能力不写成已支持。其余通用字段、五类状态与模板沿格式节。

## 6. 规则责任与上游变更边界

把产品规格的行为、权限和异常映射到唯一系统责任、数据／状态权威、接口及失败处理者；模块分工不得反向改变产品规则，工具许可仍由宿主及有效采用约束控制。模型/Agent 框架核查结果与复用边界唯一在本层维护，模块／组件引用，不在下游另造能力清单；开发发现超出已核范围时停止依赖该能力的包／任务并回本层补核，更新架构正文后再继续。未定业务回 PRD，跨模块责任冲突在本层先解决，依赖包暂停；已明确的独立设计继续。

交接列当前规则的固定来源、责任承担位置及未决影响，实施前交组件／UI 和 [阶段组织](../references/stage-methods.md#实施进入条件)核必要输入。技术探索另标对象、假设、许可及结果，不计正式功能完成；采用探索结论改变有效规则时先取得相应决定并修所属正文，不以成功试验代签。

**成果最小清单（完成前核对）：** ①端到端系统链路与边界；②路线取舍、数据／状态权威、接口；③平台／框架核查（如适用）；④当前任务及有效质量要求所需的适用设计，引用已有正文（不新增专项设计成果）；⑤兼容／迁移与运行恢复；⑥系统验证与风险；⑦模块输入与固定版本。缺①—③标缺口，不默认记架构完整。
