# 阶段方法结构与沟通粒度

## 方法怎样组织

本文件维护十阶段组织、阶段沟通、衔接与交接格式；资料身份、当前摘要与历史、项目版本计划及升版见 [项目资料、历史与版本治理](project-governance.md)，按当前任务读取。

每份方法实质回答是什么／做什么／怎么做，进一步写明模式与裁剪、有效输入／进入条件、人和 Agent 分工、有依赖的动作及沟通、输出与检查、异常／变更、完成条件、交接及停止／恢复。小任务可以合并表达，不能用标题齐全代替具体操作。成本、资源、隐私、外部依赖、迁移与兼容仅在影响本阶段时展开。

每步要能判断：依据是否足够、谁做什么、什么时候沟通或等待、成果落在哪里和是什么状态、怎么实际检查、检查后继续还是修正。共用动作引用 [execution](../rules/execution.md)；需求记录引用 [requirements](../rules/requirements.md)，每阶段只维护自己的动作、节点与内容判据。

阶段方法中的资料核对、分析、写稿及检查动作默认由 Agent 执行，用户决定的节点明确指出。任务模式优先于步骤落点，完整只读边界见 [core](../rules/core.md#只读模式与步骤权限)。以下文件落点仅用于具有相应写入许可的模式：分析／设计写在项目既有对应阶段稿，状态写在既有状态／交付记录；没有载体时只补本次必需位置。MRD／PRD 在收全确认前只写需求记录和分析材料，不写正式稿。每个节点形成后回查其输入、具体成果和下一步前置，关键决定未取得则只停依赖部分，不让“先写完后再确认”倒置顺序。

用户负责目标、优先取舍、重要范围／设计决定及指定版本批准；Agent 负责核输入、提供理由清楚的方案、执行获准工作、检查与准确报告。真实用户验收不得由 Agent 自检代签。用户新决定要回写相应正文／记录，已有授权内普通工作继续。

## 成果入口与验证载体

规划、缺失和实际形成的成果分别登记。计划路径只放计划／任务并注明规划，未形成不预填实现、验证或批准；CODEMAP／等效地图只登记核实的实际入口，已有载体优先，不为设计阶段另建代码地图。模块／组件设计形成不等于代码实现。

架构统一维护或引用系统验证策略及风险／隔离试验载体，模块、组件与 UI 只关联本层受影响事项，不另建风险系统／台账或评分体系。没有有效载体时交待验证问题、影响与所需决定；试验执行另核许可。建立关系、拆任务、交接／评审或分析需求变化前读[需求贯通方法](traceability.md)，它是唯一规范关系方法；需求—模块／组件关系沿目标项目唯一追踪入口，各层条目反向引用。开发“实现—任务—证据表”是同一关系的另一视图，引用已有具体节点，不再重复维护需求—模块／组件映射。

阶段交接沿该方法定位本次实际承接的条目、本层细化与理由、专业成果、确认范围、验收及待决影响；本文件继续维护资料／版本身份与实施前置。十阶段按真实依赖承接，不为每条需求强造十层节点；关系、语义、实际实现与验证状态分别核实。

复用或精简来源时，核对本次实际采用的正文及适用条件，把会改变执行、判断或交接的条件落到相应步骤或有效共用引用。入口、标题、编号齐全不能证明承接充分；未承接部分说明影响，不能用未来验证计划补成当前核心行为已明确。普通动作授权不替代步骤前置成果与核验。

## 按阶段沟通

不设通用次数或每操作审批。围绕用户当前能判断的事项分批展示；重要理解或选择影响后续动作时先沟通，普通进展说明具体结果和下一步。表达按 [大白话与 SCQR](messages.md)，不要把内部字段直接当用户问题。

| 阶段 | 主要沟通单元 | 应展示和需要用户决定的节点 |
| --- | --- | --- |
| 启动准备 | 目标、已有项目现状和本次许可 | 回述要做的事、可复用资料、缺口、准备成果和后续范围 |
| MRD | 一个用户问题／场景及预期效果 | 连续展示当前需求、纠正理解、冲突与首版取舍；收全后才起草 |
| PRD | 一条用户任务及相关正常／异常结果 | 展示实际操作与结果、规则和验收；逐批确认并暂存，收全后起草 |
| 架构 | 端到端链路及影响目标的技术取舍 | 方案理由、关键风险与验证限制；先确认重要选择再据此展开 |
| 模块 | 一段协作任务及职责交接 | 谁负责、传什么、失败归谁处理；确认影响分工的争议 |
| 组件 | 一个当前功能的接口／状态分支 | 输入输出、异常／未知后果、替身边界；不向用户抛每个内部字段 |
| UI | 一个可完成的任务及可见样例 | 让用户看实际措辞／原型并演示任务，记录真实理解和困难；用户确认指定 UI 版本与关键体验取舍，未确认不交开发许可 |
| 开发 | 开发包批次或完整候选版本 | 按开发方法第 2 节展示包清单、依赖路线与并行条件；合并评审回执并保留逐条理由，及时呈现必要裁决；交包成果、局部证据和未完成项 |
| 联调测试 | 一个系统任务／缺陷和验收版本 | 环境与实际结果、修复回归、用户验收及独立发布决定 |
| 迭代 | 一个有来源的反馈及候选改进 | 问题证据、影响、优先级与本轮范围；确认取舍后接续受影响阶段 |

同一节点不因更新文件而重问；阶段切换、重要变更和待决按共用触发呈现。完成后交指定成果与真实检查，停止在当前授权边界；恢复读当前对象／版本、决定及未完成事实，不把历史证据当本次执行。

## 阶段衔接总表

下表是十阶段接续的导航，不新增强制流程；输入、产出与交接物仍按各阶段方法及实际依赖展开。已有项目从实际阶段接续，不因本表强制回到启动或 MRD。表中“版本基线表”指 [文件版本与产品基线](project-governance.md#文件版本与产品基线)。

| 阶段 | 主要输入 | 本阶段产出 | 交接包去向 | 进入下一阶段的许可 |
| --- | --- | --- | --- | --- |
| 启动准备 | 用户请求、已有项目资料、当前许可 | 准备结果（目标／范围、资料与状态、入口） | 新建→MRD；已有→实际阶段（对象见版本基线表） | 新建：用户确认准备＋MRD 许可；已有：实际阶段与当前任务许可 |
| MRD | 需求记录、证据、约束 | 正式 MRD（含产品类型基线） | → PRD（对象见版本基线表） | MRD 通过＋PRD 许可 |
| PRD | MRD 与确认 | 行为／异常／验收／追踪、自检、独立评价 | → 架构（对象见版本基线表） | PRD 指定版本确认＋架构许可 |
| 架构 | PRD、产品类型基线 | 链路／数据／接口／风险验证、运行恢复；使用框架时含框架核查与复用边界；平台有官方规则时含平台核查结果与约束／待办 | → 模块（对象见版本基线表） | 架构确认＋模块许可 |
| 模块 | PRD、架构 | 职责／状态权威／协作契约／走查 | → 组件（对象见版本基线表） | 模块确认＋组件许可 |
| 组件 | 需求、架构、模块 | 契约／状态异常／用例／走查 | → UI 或开发（对象见版本基线表） | 组件确认＋UI／开发许可 |
| UI | PRD、组件 | 流程／状态文案／样例／演示／检查 | → 开发（对象见版本基线表） | UI 确认＋开发许可 |
| 开发 | 规格／设计／环境、产品类型基线与已核框架范围 | 开发包合同、实现、局部证据；复用框架前引用架构已核范围＋本轮复用决定（不另造清单） | → 联调（对象见版本基线表） | 包完成＋联调许可 |
| 联调 | 实现／环境／验收 | 系统结果、缺陷回归、用户验收 | → 迭代（对象见版本基线表） | 验收结论＋迭代许可；发布另核，不作为迭代前置 |
| 迭代 | 有来源的反馈、现行版本（未验收／未发布也可按许可分析） | 变更范围、接续层、验证、效果观察 | → 受影响阶段或下一轮（对象见版本基线表） | 用户确认本轮范围＋按需阶段许可 |

本表只作阶段导航与许可；“交接包去向”的对象提示不替代“版本基线表”，交付前应固定／引用的对象以该表为准。首版可先覆盖当前一条核心用户任务链，逐层只写该链路，其余标计划或未形成；不新增强制阶段，也不取消各阶段确认。阶段可因实际依赖跳过、并行或回退，省略层须说明依据。返回修订沿 [execution §10](../rules/execution.md#10-评审意见返修与成果确认)，版本固定仍沿[文件版本与产品基线](project-governance.md#文件版本与产品基线)。

## 阶段交接物格式

阶段交接包是已有对象的组合引用，不新增存储或第二权威；按下列最小字段组织为结构化 Markdown（固定键名，未知项写明状态，不写成散文清单）。日常局部任务可只交实际结果、必要证据、限制和接续；只有跨阶段、跨执行者或正式评审／验收／发布才按本表组织，未触发时不生成无关阶段包。交付消息建议简交时，仍须保留“跨阶段、跨执行者或正式评审／验收／发布按正式交接”的条件；不得仅以同模块或等义修改概括。局部修改若改变产品行为或含义（包括文案），仍须按对应阶段核影响，不能仅因改动范围小视为等义简交。

| 字段 | 内容 | 缺失／状态处理 |
| --- | --- | --- |
| 上游依据 | 本次直接消费的有效上游对象／条目、固定版本、确认范围；沿[需求路径入口](traceability.md#5-交接与评审的路径入口)追溯至 MRD 或经确认等效依据 | 版本未知标未知；依据不足限制依赖 |
| 承接条目 | 具体需求／验收 ID 与本次承接子集、理由 | 适用但缺失记缺口；有依据不适用说明依据 |
| 本层产出 | 成果对象、版本、状态（候选／已确认／未形成）、边界 | 未形成只标计划或未形成 |
| 异常与后果 | 从 PRD 起适用；相关业务异常在 PRD 明确、下游引用；尚未决定的列待决及影响；技术／接口／交互细节留给对应设计阶段。启动／MRD 尚无业务异常时填“本阶段尚无需细化”及依据，不用“无”占位 | 适用且应明确但缺失记缺口；有依据不适用、本阶段尚无需细化（注明留层）、未知分别标注；确无写“无” |
| 验收与验证 | 判据、计划／执行状态、证据定位 | 未执行不写通过；确无写“无” |
| 待决与未验证 | 未决项、影响、解除条件 | 确无写“无”；其余按上列状态 |
| 下一层输入与许可 | 下一层动作、输入、所需许可及等待对象 | 许可未取标明等待；不适用说明依据 |
| 路径引用 | 需求路径入口（第 5 节）或本阶段实际适用依据 | 缺入口记入口不足，不因缺路径判目标不合格 |

交接双方、确认依据、确认时点与接收状态沿既有确认记录或消息引用，不新增必填字段、不另建台账。状态用语只用于缺失项与适用性说明：缺口／有依据不适用／本阶段尚无需细化／未知／无。产出生命周期与许可状态分别沿权威对象实际状态记录，不用上述五类替代。状态按来源支持的对象和范围记录；不得仅凭未提供、未观察到或本轮未制作，推断项目对象不存在或从未形成。项目既有状态缺乏依据时保持未知；来源明确确认的状态按事实记录。交接包只引用各阶段唯一正文，不复制内容；空引用须说明原因；字段可因阶段裁剪，但被裁剪字段同样说明状态。各阶段方法交接段只给本阶段示例，未列字段按本表补齐；模板见 [交接包组织提示](../assets/templates/handoff.md)。

## 评审返修与交接

十阶段共同沿 [execution 第 10 节](../rules/execution.md#10-评审意见返修与成果确认)处理意见、返回受影响步骤、实际复查和核指定成果结论；各方法只保留本阶段检查／交付落点，不另维护十份返修规则。用户评审结论与下一阶段许可分别核对；需求变化涉及收全／版本确认时沿 [requirements 第 3 节](../rules/requirements.md#3-收全后起草)处理，只重核受影响范围。

## 规则职责与采用

三类约束与采用边界沿 [core 三类约束](../rules/core.md#三类约束与采用边界)。项目既有采用索引维护唯一来源、适用条款、固定提交／blob、实际决定、责任人与回退；若用结构化登记，索引只作指针，须逐条核身份与引用一致，不能并存两个采用权威。没有既有采用记录时沿 core 的回退顺序（用户有效规则／当前引用正文＋身份未核缺口），不新建 schema。产品运行资源可独立交付，不依赖作者项目台账。

用户决定产品目标、重要规则／取舍、项目约定及指定版本；Agent 提出方案、维护获准正文、执行与自检；宿主约束实际工具权限。实施者身份须来自实际任务／委派，独立评价方须另核来源、独立性、范围及许可，不从“审计方”称谓或开发者自检推定已经落实。冲突回规则所属责任层，相关动作等待，已有明确许可内的独立部分继续。

## 实施进入条件

本“实施进入条件”小节是 [development.md §2](../skills/development.md#2-明确一个功能合同和顺序)合同字段清单的补充，经该文文首“共用动作见 阶段组织”承接；开发建包时在既有合同内形成或刷新本小节，上游（需求／组件／UI）只在交接包交可引用条目，不写下游合同；不另建合同、模板或台账。

按实际依赖完成当前范围的有效需求、系统／模块责任与必要契约；适用时完成 UI 交互与可见后果（不要求所有包先经 UI）。每个当前开发包在既有合同的“实施进入条件”小节逐项引用下列落点。Agent 核对，重要缺口交用户决定，不以口头自检或标题打勾代替：

1. 有效需求／设计标识、固定版本和范围，能溯源到实际确认。
2. 正常及相关异常结果、权限和数据后果；有官方规则时含平台约束与待办；具体正文分别在 PRD、组件与 UI。
3. 实现执行者、接口／状态权威及失败处理负责人，职责与许可可核。
4. 验收与验证依据、可观察结果及实际可用验证入口，计划和证据分开。
5. 未决项、受影响包、解除条件及可进入／等待判断；关键业务未定只停依赖包。

组件与 UI 负责对应输入交接，开发方法负责包／路线和执行；技术探索注明假设、范围、许可及结果，不计正式包完成。无需在首次开发前定完未来全部细节。已授权设计／候选制作不等于指定设计版本通过，进入依赖实施仍核实际前置。

人工交接核对不伪造工具调用；实际调用宿主工具时保留真实返回并用于判断，工具成功或退出 0 不代用户签认。工具选择与缺能力处理沿[工具使用与检查](checking.md)，沿现有合同和状态记录，不强制新增模板、台账或自制工具。
