# 需求贯通：关系、溯源与专业交接

## 何时读、各自负责什么

接续既有需求、把要求转成本层成果、拆开发任务、交接／评审或分析需求变更时读本方法。它是包内**唯一规范关系方法**；各阶段只补本层动作。需求追踪是维护和查询双向关系，溯源是从成果反向核实原始要求、确认与有效变更；追溯泛指沿关系查上下游或历史。贯通指这些关系在多阶段持续承接的效果。

沿目标项目已有唯一追踪表、文档分区或等效位置维护实际关系，不要求新文件、编号前缀、数据库或图谱服务。项目已有多个候选载体时，先在需求记录／当前状态声明唯一关系入口、覆盖范围及用户确认，其余作为视图或引用；不得据此新建第二份映射；没有现成载体时可在既有文档分区内指定，不强制新系统。正式行为仍在有效规格，确认／变更仍在已有记录，原始结果仍在相应证据中，关系只引用。需求来源与确认沿 [requirements](../rules/requirements.md)，版本／资料治理沿 [stage-methods](project-governance.md#project-material-version-governance)，动作许可沿 [core](../rules/core.md)。只读模式只在回复中交关系发现与建议，不写入。

## 1. 从真实来源建立关系

先定位本次有效目标、具体需求／约束、用户确认及取舍，保留实际内容身份和范围。有 MRD 时追到具体条目；已有项目没有 MRD 时用经确认的等效依据，并说明覆盖／缺口。不补造 MRD、历史批准或未来成果。来源不足只限制依赖分支，未受影响内容沿用。

在现有载体中补足以下信息，已有内容直接引用，不为凑字段复制：

| 对象 | 至少能核实什么 |
| --- | --- |
| 节点 | 稳定标识、具体正文位置、内容／版本身份、范围、真实状态和适用确认；包括需求／约束、设计、开发包／任务，以及分别定位的实现、用例、证据 |
| 关系 | 上下游具体条目、关系含义、实际承接的要求／验收子集、承接理由或具体落点，及待核实影响 |
| 状态 | 规划／实际形成、已确认／拟议／待决、未执行／实际结果分别可辨；未到阶段、延期或不适用有真实依据，不预填实现或证据 |

实现是实际产出的代码、配置或技能正文；用例是验证的前置、操作与预期；证据是对指定对象实际执行后的原始观察／返回。三者分别引用，用例存在不等于已执行，实现完成不等于验收通过。

细化（原目标→具体行为）、承担（要求→设计责任）、实现（要求／设计→任务及产出）、验证（要求／验收→用例→受测对象及结果）、变更（旧要求→决定→新要求及影响）各写清含义。顺序依赖只说明先后，不能单独证明任务的需求来源。编号和连线存在不证明内容承接正确。

允许一对多、多对一及共享节点；同一节点只有一个正文身份，各来源分别说明承接子集与理由。不要求每条需求经过十层，也不把 UI 强插进无交互需求；跨层消费按实际依赖定位，省略层说明不适用或由何处直接承接。

## 2. 任务级溯源与双向核对

展开开发包时，每个任务引用实际需求／验收子集和设计落点，沿关系可反查到具体原始要求及有效决定。可以继承包的固定基线，但不能只挂整包、整份 PRD 或笼统目标。共用技术／测试任务说明支撑哪些要求或约束、各自必要性；无法说明时先报告并澄清，不能硬挂编号或擅自新增工作。

开发“实现—任务—证据表”是同一关系的另一视图：引用已有任务、实现和结果节点，需求—模块／组件映射仍沿唯一追踪入口，不另维护第二份映射。其他视图同样从现有关系选取所需信息，不独立定义需求、确认或状态。

成果形成、交接及相关变更后，沿 [requirements §4](../rules/requirements.md#4-成文检查与交接)核成文落点，按 [execution §9](../rules/execution.md#9-检查动作与结论)先定对象／判据、实际检查，再给对应结论：

1. **正向覆盖：**从本版每项原要求查本层具体落点及验收／计划验证；未纳入者核有效取舍。未形成的下游保持计划，不强填落点。
2. **反向来源：**从本层每项行为、设计和任务查具体要求及必要性；发现孤立成果、漏列共享来源或仅有依赖线时补核，不把作者自定验收当原始要求。
3. **语义承接：**对照原文及有效决定，核目标、范围、角色／责任、前置、顺序、规则、异常／数据后果和验收是否保持；说明本层怎样满足上游，不只数编号。只核实际相关条件，不给所有需求硬加异常分支。
4. **版本与状态：**核实际消费的固定内容、确认范围、受测对象与证据覆盖。分别报告关系已建立、语义已核对、实现已形成、实际验证和用户验收，不能互相代签。

编号全对但含义偏移仍是偏差；缺资料／未查明则是证据不足。关键缺口限制相关分支，沿 [execution §10](../rules/execution.md#10-评审意见返修与成果确认)交付及返修；不自动重开全部上游阶段。

独立评价在 [independent-testing](../rules/independent-testing.md) 的适用范围及实际安排内使用本方法，评价方从固定原始依据自行核实关系、覆盖与含义，作者关系只作定位材料；本次上下文按第 5 节路径入口取得。读取上游用于判断本次对象，不扩为对全部上游的重新评价；本方法不新增十阶段独立评价门槛。

## 3. 回述确认与专业交接

消歧与回述确认的操作正文唯一在 [requirements §1](../rules/requirements.md#1-边沟通边保存)；本节只保留转写与专业交接的落点要求。

回述、确认、保存、普通同义整理及不回问判据按 [requirements §1](../rules/requirements.md#1-边沟通边保存)执行，本节不重复；本节的转化依据、承接理由、交接精度与待决／边界要求仍是本节规范。Agent 先区分要求、背景、示例、建议及假设；沟通样例见 [messages](messages.md)。

转写核已确认目标、范围、条件与预期等义。**转化**为本层设计／任务会增加细节，须说明依据及承接理由；产生新的重要业务选择时按 requirements §1 回用户决定，不能以“专业化”掩盖默认取舍。确认、收全及正式稿通过仍沿 requirements，不合并。

交给下一阶段时定位：有效输入及实际承接条目、本层细化与理由、具体成果位置／内容身份、适用确认、边界和异常、验收／验证依据、待决影响与继续条件。术语、前置、输入输出、规则、责任和可观察结果达到该阶段无需猜测关键行为的精度；已有正文足够则引用，不复制规格或提前补齐未来所有细节。用户可见说明继续用大白话，内部专业表达不能静默改变已确认含义。

## 4. 树状概览与变更

用户需要看需求发展过程时，从唯一关系入口按一条需求展开 Markdown 树或 Mermaid 图，附所依据的范围／固定版本和实际状态。共享节点复用同一标识，以交叉引用保留多来源；不复制成不同任务。图是关系视图，不能代替专业正文、确认记录或原始证据。关系变化后重绘；交接前核图与正文同版，过期图先标明不能据其判断。

需求变化沿 [requirements §2／§3](../rules/requirements.md#2-改动与冲突)保留原／新内容、原因及用户决定。沿双向关系定位受影响的设计、任务、实现、用例、证据和实际消费者，结合语义判断失效范围；不能只因处于同一树下就认定全部失效，也不能只改连线就沿用旧通过。同步与再次变化按 [版本治理](project-governance.md#project-material-version-governance)处理，真实写入及必要复核后才更新状态，无关有效分支继续。

## 5. 交接与评审的路径入口

阶段交接、独立评价或用户需要看一条需求的发展过程时，从第 4 节树状视图或目标项目已有关系入口，按一条需求给出可定位的路径引用；按需展开，不默认每次任务都生成整条视图。

路径引用至少能定位：需求标识（MRD 或经确认等效依据的条目、固定版本、确认状态）；目标／问题与范围／非目标条目；**产品类型基线**（MRD 必答六项或经确认等效依据；本文件只引用，不重列清单；缺失按未知或不适用＋依据）；下层节点（PRD 行为／验收 → 架构责任／接口 → 模块 → 组件 → UI → 开发任务／实现 → 用例／证据 → 迭代变更），每节点给对象或正文位置、版本或未知、实际状态及共享来源。只引用各阶段唯一正文，不复制内容、不另建台账、不要求每条需求单独建文件。

共享节点保留全部来源及承接子集；允许跨层，须说明依据；下游未形成只标计划或未形成；不适用须有依据。基线或依据变化时，先判影响、只标具体失效范围，未受影响依据沿用；旧证据复用须仍覆盖本次对象与条件。

阶段交接包引用本路径入口；独立评价按本轮范围读取，不扩为全部上游重审。发出前核路径与正文同版；过期路径标明，不据其判断。

完整示例与图示见 [需求贯通示例](traceability-examples.md)；示例只说明关系用法，不构成需求或确认。
